## 三、认证体系：严格区分四种角色

这是不可违反的业务要求。

### 3.1 普通用户：微信登录

未来正式环境采用微信开放平台网站应用扫码登录。

Mock 阶段提供独立的 Mock 身份提供方，用于 Staging 开发和测试。

登录成功后：

- 关联现有 PostgreSQL 用户。
- 建立或复用现有服务端会话机制。
- 使用现有 HttpOnly Cookie 和用户认证 Guard。
- 保留用户订单所有权检查。
- 支持退出登录和会话吊销。
- 不得因为微信登录而绕过现有账号状态、业务权限或订单校验。

### 3.2 打手 / 护航：微信登录

打手同样使用微信登录，但必须与普通用户的身份和授权流程区分开。

要求：

- 微信身份只能关联经过系统创建、绑定或审核的打手账号。
- 不允许微信授权成功后自动获得打手角色。
- 不允许客户端通过提交 `role=companion` 等字段提升权限。
- 不允许根据昵称、头像等可变资料自动绑定已有打手账号。
- 必须验证账号状态、打手身份、会话类型和服务端授权。
- 未授权用户不得访问打手工作台、订单池、专属池、收益及其他受保护接口。

如果现有业务没有安全的首次绑定流程，应实现明确的绑定或审核流程，不要擅自推定微信身份与已有账号的对应关系。

### 3.3 客服：继续使用账号密码

客服账号由系统或管理员创建。

必须保留：

- 现有账号密码登录。
- 密码哈希验证。
- 独立客服会话和权限检查。
- 改密、密码重置及会话吊销。
- 现有订单处理、接单、审核等业务权限。

不得给客服增加微信登录作为默认入口，不得让普通用户会话被识别为客服会话。

### 3.4 管理员：继续使用账号密码

管理员使用系统创建的管理员账号密码登录。

必须保留：

- 现有管理员登录与会话。
- 管理员专属 Guard 和服务端权限验证。
- 改密、密码重置及相关审计。
- 现有管理业务权限。

不得使用微信登录替代管理员登录，也不得因微信身份绑定、用户注册或打手授权而授予管理员权限。

### 3.5 认证和会话的共同原则

优先复用现有真实认证及会话设施，不要创建重复的通用用户表、密码表或会话表。

必须验证：

- 用户不能访问客服、管理员和打手专属接口。
- 打手不能自动获得管理员或客服权限。
- 客服不能访问管理员专属接口。
- 未认证请求不能执行受保护操作。
- 伪造请求体中的角色字段不能改变权限。
- 已吊销、过期或失效的会话不能继续访问受保护资源。
- 真实认证失败不得静默回退到 Mock 身份。
- Mock 登录与真实微信登录必须明确区分。

## 四、微信登录实现要求

### 4.1 提供方设计

设计清晰、独立的身份提供方接口，至少区分：

- Mock 微信身份提供方：供 Staging 使用。
- 真实微信网站应用身份提供方：待平台配置完成后启用。

不要将 Mock 逻辑散落到正式微信回调处理代码中。

真实微信配置缺失时，明确显示“微信登录尚未配置”，不能伪造真实微信授权成功，也不能默认将 Mock 结果当成真实身份。

### 4.2 真实微信 OAuth 流程

为未来正式接入实现或预留以下流程：

1. 发起微信网站应用扫码授权。
2. 生成并验证一次性 `state`，防止 CSRF。
3. 校验回调参数和授权结果。
4. 使用服务端凭据交换授权码。
5. 按平台实际能力获取微信身份信息。
6. 通过稳定的提供方标识识别微信身份。
7. 查找已有身份绑定，或进入明确的新用户注册、绑定流程。
8. 关联现有 PostgreSQL 用户。
9. 建立现有会话。
10. 按服务端角色与账号状态进入相应页面。

要求：

- 正确处理 AppID、OpenID，以及平台允许获取时的 UnionID。
- 唯一约束必须防止重复绑定、并发注册和身份冲突。
- OpenID 必须结合对应的微信应用身份范围处理，不能假定所有应用共享相同 OpenID。
- 不得按昵称、头像或其他可变信息自动合并账号。
- 重复回调、过期授权码、无效 state、用户取消授权和网络失败必须有明确处理。
- 回调地址、AppID 和相关参数必须配置化，不得硬编码临时 IP、本地地址或未来域名。
- AppSecret 等凭据只允许存在于受保护的服务端配置中，不得提交 Git、输出到日志、进入前端 bundle 或写入聊天记录。
- 在正式平台配置、域名及 HTTPS 条件不满足时，不宣传真实微信登录已经可以公网使用。

如果缺少平台凭据，优先完成可独立测试的适配器结构、Mock 闭环及真实适配器的安全实现；对必须依赖平台配置的部分明确标记待人工完成，不得伪造验证结果。

## 八、自动化开发与部署

遵循现有工作流：

代码开发 → 单元与集成测试 → typecheck → lint → build → Git 提交与普通推送 → CI → 构建产物校验 → 上传 → 现有受控入口部署 → 数据库迁移 → 健康检查 → 真实浏览器验收 → 失败时回滚。

要求：

1. 普通业务代码修改优先通过现有受控部署入口自动发布到 Staging。
2. 不为方便而配置 `NOPASSWD ALL`。
3. 不允许 `deploy` 修改 root 拥有的可信脚本。
4. 不绕过现有产物校验、数据库隔离和权限边界。
5. 不修改 SSH 安全配置。
6. 不开放 3000 或 5432 公网端口。
7. 不重置或清空 Staging，不修改生产数据库。
8. 对需要 root 可信脚本更新、系统配置变化、权限扩大或无法安全自动回滚的操作，先说明具体变更、风险、校验和回滚方式，等待人工授权。
9. 普通代码发布不得因为没有新的高权限变更而重复要求人工输入 sudo 密码。
10. 如果现有架构阻碍普通业务自动发布，先分析最小改进方案，不得直接扩大权限绕过限制。

每次部署后核对应用 Git SHA、产物 SHA-256、迁移版本、服务健康状态及数据库隔离结果。

## 九、执行顺序与阶段交付

请按以下顺序推进：

**阶段 A：审计。** 输出现有架构、复用点、差距和最小改动方案。

**阶段 B：实现。** 完成 Mock 微信身份提供方、真实微信适配器结构、身份绑定机制和必要的增量迁移；保留客服、管理员账号密码登录及现有 Mock 支付。

**阶段 E：浏览器验收。** 实测认证、身份绑定、权限隔离、模拟支付及数据持久化。

**阶段 F：交付。** 输出修改文件、迁移编号、测试结果、CI 结果、实际部署 SHA、浏览器验收结果、未完成事项及回滚方式。

如果某个阶段失败，先根据实际错误定位并修复，再重跑相关测试。不要仅因为本地测试通过就声称部署完成。
