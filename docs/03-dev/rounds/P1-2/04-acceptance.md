### 1.2 ⚠️ 三个会让验收得出**错误结论**的坑

1. **「超时转公共池」是惰性的**——没有定时器，**有人读才清扫**。
   因此「到点了怎么还在专属池」不是缺陷：打开一次打手工作台（`/companion/exclusive` 或 `/companion/pool`）、

2. **改配置不会立刻改变任何已经存在的单**，这正是本轮要证明的事。
   看到旧单「没动」是**正确结果**，不是没生效——新单才会用新值。

## 二、验收清单

### A. 配置页：四项都看得见，且**不是只写一个数字**

1. 以**管理员**打开 `/admin/platform-config`。
2. **预期**：
   - 有**四个**输入框，自上而下：**专属订单池超时（分钟）** / 公共订单池超时（分钟） /
     完成材料自动审核时长（分钟） / 投诉窗口（分钟）；
   - **专属池那一项在最前面**（本轮新增，且是产品裁定里最要紧的一项）；
   - 每个输入框下面都有**业务含义说明**，不只是一句「可填 1~1440」：
     专属池那条应写着「**指定打手在此时间内拥有独占接单权；超时后进入公共接单池。
     修改后仅影响之后进入专属池的订单。**」；
   - 输入框下方的「当前值」区列出**四项当前值**（形如「专属池超时当前值：10 分钟」）
     以及 **最后修改时间** 与 **修改者**（预置数据时显示「预置值，尚无修改记录」）。
3. ⚠️ **不得**只显示「超时：10」这类既没有单位、也没有「改了影响谁」的写法。
   这一条是**产品原文明令**的（`01-prompt.md` §十），请逐字对照。

### B. 保存：成功 / 无变化 / 失败 三种反馈都要有

1. 把 **专属池超时** 从 `10` 改成 `30`，点 **保存**。
2. **预期**：
   - 出现绿色成功提示，**逐项列出四个当前值**，并说明「此后新发生的事按新值判定；
     已进入专属池 / 公共池的订单……沿用各自冻结的快照，不受这次修改影响」；
   - 「最后修改」时间戳**变了**，「修改者」显示 `admin-1`；
   - **刷新页面（F5）** 之后仍是 `30`——说明真的写进了服务端，不是只有前端 state 变了。
3. **「没有变化」不算保存成功**：不动任何输入框时**保存按钮是灰的**（点不动）；
   若把某项改回原值再点，应提示「取值没有变化，未写入。最后修改时间也没有变动。」
   且**「最后修改」时间戳不变**。
4. **服务端校验**（不是只靠浏览器）：在专属池输入框里填 `0`，点保存
   → **预期**：红色错误提示「专属池超时必须是 1~1440 之间的整数分钟」，**不发请求成功、不写入**。
   再试 `1441`、`1.5`、`-1` 应同样被拒。
   ⚠️ 若用浏览器开发者工具直接 `PATCH /api/admin/platform-config`
   提交 `{"exclusivePoolTimeoutMinutes": 9999, "idempotencyKey": "..."}`
   → **预期**：接口返回 **400**，文案与页面上那句**完全一致**（同一份常量）。

### C. 只改一项不碰另外三项

1. 先看「当前值」区，记下另外三项：公共池超时、完成材料自动审核时长、投诉窗口。
2. 只把 **专属池超时** 改成另一个值并保存。
3. **预期**：另外三项的当前值**一个都没变**（既没被清空，也没被重置成默认值）。
   （这一条防的是「保存一个字段顺手把整份配置重写一遍」。）

### D. ⭐⭐ 本轮核心：**旧单不变、新单用新值**（**全程即时可判，不用等**）

> 这组是本轮存在的理由。**只要有一格不符，本轮即为 FAIL。**

**D.1 造一张「已进入专属池」的单（用一个小一点的时长，好观察）**

1. 先把 **专属池超时 = 30** 并保存（§B 已改到 30 的话跳过）。
2. 切到**老板 A**，下单：商品任选 → 去结算 → **「推荐陪玩」点进去，选「夜航」** → 提交支付
   → 在支付结果页点 **「模拟支付成功」**。
   （⚠️ 这一步的关键是**在结算页指定了打手**——不指定的话订单直接进公共池，验不了本轮。）
3. 切到**夜航**（`u-1022`）→ 打开 `/companion/exclusive`。
4. **预期**：这张单出现在**专属池**里，卡片上写着「**剩余 29 分钟**」（或 30 分钟；取决于你点开的速度）。
   ⚠️ 记下这个数字，记为 **旧单剩余时间**。

**D.2 把配置改大 —— 旧单**必须**不动**

1. 切回**管理员**，把 **专属池超时从 30 改成 1440**（24 小时），保存。

   ✅ 这就是「已经进入专属池的订单沿用进入时冻结的时长」。
4. ⚠️ **反例（必须确认没有发生）**：如果这里显示成了「**1439 分钟**」，
   说明实现是「每次读最新配置重算截止时间」，**本轮 FAIL**。

**D.3 新单必须用新值**

1. 仍然以**老板 A**，**再下一单**，同样在结算页**指定「夜航」**，支付成功。

   ✅ **一屏之内同时看到「旧单没变」与「新单变了」**，这是本组最直接的证据。

## 三、通过标准（PASS / FAIL）

**PASS 的条件（全部满足）**：

- §A 四个字段都在，专属池**有业务含义说明**（不是只有一个数字），当前值区完整；
- §B 保存的三种反馈（成功 / 无变化 / 非法）都符合预期，刷新后值仍在；
- §C 只改一项不动另外三项;
- §D **在改大配置之后，旧单剩余时间不变、新单用新值**（一屏可同时看到）——**本轮最核心的一条**；
- §F 匿名 / 用户 / 打手 / 客服**四条拒绝**、管理员**一条放行**（读与写都验）；
- §G 每次真改动有一条带 `before` / `after` 的审计；

**FAIL 的判定**：上述任一条不满足，或出现下列任一种情况——

- 改了配置之后，**已经进入专属池的旧单的截止时间跟着变了**；
- 改配置时**顺手把另外三项重写/清空/重置成默认值**；
- 非法取值（`0` / `1441` / `1.5` / 数字字符串）被**静默接受或夹取**成某个合法值
  （例如提交 `9999` 却写进去 `1440`，或提交 `0` 却写进去 `10`）；
- 非管理员**能读到或能改动**平台参数；
- 页面上**只有「超时：10」**那样既无单位、又无「改了影响谁」的写法；
- 「值没有变化」的保存**刷新了最后修改时间**（那个字段是证据，不能被空保存推动）。
