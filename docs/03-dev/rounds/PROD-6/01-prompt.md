# PROD-6：实现真正的公网登录，而不是 SSH 私有登录

Round: PROD-6
Received At: 2026-10-20
Source: User

---

现在纠正项目开发方向。

此前 PROD-4 和 PROD-5 已经开发了真实认证、Mock 微信登录、身份绑定以及数据库订单等能力，但验收主要在 SSH 隧道内完成。

我的实际目标是：

**普通用户无需 SSH 隧道，直接在公网网站访问登录入口；客服和管理员也能够通过公网登录自己的工作台。**

不能再把「SSH 隧道内登录成功」作为公网登录任务的完成标准。

## 1. 认证规则

- 普通用户：微信登录。
- 打手：微信登录，必须经过系统角色授权。
- 客服：管理员或系统创建的账号密码登录。
- 管理员：系统账号密码登录。

客服和管理员的登录页面必须允许公网访问，进入工作台和执行操作时才进行身份验证及权限控制。

## 2. 先审计公网阻断原因

请定位：

- Nginx 公网白名单。
- Next.js proxy.ts 公网守卫。
- 用户、打手、客服、管理员的登录页面与 API。
- 现有 Session Cookie、权限 Guard 和数据库访问。
- 当前公网服务器和私有 Staging 是否共用进程、数据库及 Mock 开关。
- HTTPS 与域名的准备情况。

明确每一项阻断的具体代码位置和修复方式。

## 3. 优先实现公网客服与管理员登录

目标行为：

- 未登录访问 /staff，跳转 /staff/login。
- 未登录访问 /admin，跳转 /admin/login。
- 公网登录页面能够正常打开。
- 登录 API 验证 PostgreSQL 中的真实账号。
- 登录成功进入对应工作台。
- 退出登录后不能继续操作。
- 客服不能进入管理员后台。
- 普通用户不能调用客服和管理员接口。
- 未授权操作由服务端拒绝，而不是仅靠隐藏前端页面。
- 排查已有客服账号 kefu-xiaoyu 的 401 问题，不擅自重置其密码。

正式开放必须先完成 HTTPS、登录限流、CSRF 防护和安全 Cookie 配置，不允许在明文 HTTP 上传输真实密码。

如果缺少域名、DNS 或 TLS 配置，需要我操作，请明确列出所需的最少人工步骤。不要因此停止所有不依赖域名的代码开发与测试。

## 4. 用户与打手微信登录

保留现有 PROD-5 微信 OAuth 实现。

为公网微信登录准备页面、回调路由及身份绑定流程。

但没有真实微信 AppID、AppSecret、授权域名和 HTTPS 时，不得声称扫码登录已经可用。

Mock 微信登录继续留在私有 Staging，不允许暴露为公网真实登录。

## 5. 公网安全策略

重新设计 Nginx 和 Next.js 的公网访问策略：

- 匿名访客可以打开公开页面和对应登录页面。
- 登录和 OAuth 回调只允许必要的接口。
- 登录后的功能由服务端会话及角色权限控制。
- 不使用直接开放全部 /api/* 的方式解决问题。
- 不开放调试、身份冒用、Mock 登录、Mock 支付和未经授权的危险接口。
- PostgreSQL 仍不对公网开放。
- 未完成安全审核前，不直接将现有 Staging 当作正式生产环境。
- 任何生产环境、数据库或公网权限变更均需事先列明并取得必要授权。

## 6. 交付标准

请不要只提供代码测试通过的报告。

最终验收必须是：

在一台没有 SSH 隧道的普通设备上，通过公网 HTTPS 地址：

1. 打开客服登录页面。
2. 使用真实客服账号登录。
3. 进入客服工作台并完成授权操作。
4. 退出登录。
5. 打开管理员登录页面。
6. 使用真实管理员账号登录。
7. 进入管理后台并完成授权操作。
8. 验证错误密码、未登录访问和跨角色访问均被拒绝。

微信登录另列真实平台联调结果，未配置不得标记成功。

允许你自主完成现有权限范围内的代码修改、测试、CI 和 Staging 部署。

涉及域名、HTTPS 正式部署、Nginx root 配置或公网生产权限变化时，给出需要我批准的具体步骤。

最终报告必须明确区分：
- 私有 Staging 功能完成。
- 公网 HTTPS 登录功能完成。
- 微信真实平台授权是否完成。

请先审计并给出最小实施方案，然后连续推进可以安全执行的开发任务。
