### C.3 ⚠️ `P0-13` 的 BLOCKER B-1 —— 本批次唯一一个**真缺陷**

**症状**：一张 `serving` 单可以带着 `refundedAmount = 300` 被打回 `paid`，再退 1000 ⇒
**累计 1300 > 实付 1000**。用户被多退了钱。

**触发链（三条缺一不可，因此很难从单点看出来）**：

1. `applyOrderRefund` 第三个参数的**语义**从「覆盖成这个值」改成「**本次的增量**」；
2. **部分退款不改订单状态**（P0-13 的新规则）⇒ `serving` 可以带着非零的 `refundedAmount` 存在；
3. **P0-11 的 `releaseOrderByStaff` 不动 `refundedAmount`** ⇒ 打回 `paid` 后这个数被**保留**。

三条叠加后，两条**全额**路径（直接退款 / 公共池超时自动退款）**仍然传实付全额**。
⚠️ 更要命的是：`NaN` 类保护**咬不住**它——`NaN <= x` 恒为 `false`，
因此 `assertRefundAmountWithinPaid` 这一路上**不会报错**。

**可达性**：**只靠种子数据就能到达**，不必走 P0-11 的回池路径——
`ord-seed-1002-01` 是 `paid` 且带一条预置 `pending` 退款 `rf-seed-1002-01`，
而 `approveRefund` **没有订单状态守卫**，管理员批 30% 后订单**仍是 `paid`**、`refundedAmount = 300`，
直退按钮随即出现。

**修法（三层）**：

| 层 | 改动 | 为什么在这一层 |
|---|---|---|
| 调用方 ×2 | `directRefundTransaction.ts` · `companionDispatchTransaction.ts` 改传**差额**（实付 − 累计已退） | 传「实付」在部分已退的单上**语义就是错的** |
| **写入器** | `applyOrderRefund` **自己钳一次**（`0 ≤ refundedAmount ≤ actualPaidAmount`） | 把不变量钉在**唯一写入点**——符合本仓「唯一真值源」纪律，而不是指望每个调用方都算对 |
| 界面 | `DirectRefundButton` 报出**本次实际**金额，并说明「此前已退回多少」 | 不解释的话，用户会以为**平台少退了钱** |

**回归保护**：新增 3 条组合路径用例，并做**受控 mutation** 证明它们**真会红**：
去掉写入器钳制 → **仍绿**（证明调用方是对的）；**再**去掉两处调用方 → **26 pass / 3 fail**。

**为什么既有 1374 条用例一条都没咬住**（这是 M-1 的内容）：**所有套件都从 `refundedAmount === 0`
的干净订单出发**——「部分已退」这个前置状态在测试里**从未出现过**。
