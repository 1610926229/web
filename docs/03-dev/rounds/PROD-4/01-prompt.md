## 一、优先审计现有项目

不要直接重写已有系统。

先阅读现有代码、数据库 Migration、接口、用户端、管理员后台及客服工作台，确认：

1. 哪些功能已经真实实现？
2. 哪些只依赖 Mock 数据？
3. 哪些已使用 PostgreSQL？
4. 哪些功能只有页面，没有完整业务逻辑？
5. 哪些接口存在权限、并发或状态一致性问题？

输出简洁的功能矩阵，区分「可用」「部分可用」「未实现」。

## 二、实现最小真实业务闭环

目标不是一次性开发完整商业平台，而是使以下流程真实可运行。

### 1. 用户账号

- 注册、登录、退出登录。
- 使用现有认证架构，优先复用已有功能。
- 如果没有完整的真实认证，可优先设计邮箱密码登录，不急于接入付费短信服务。
- 密码安全哈希存储。
- Session/Cookie 安全处理。
- 用户只能查看和操作自己的数据。
- 管理员、客服、普通用户权限严格区分。

### 2. 商品与订单

- 从 PostgreSQL 加载真实商品、价格、规格和上下架状态。
- 用户选择商品和规格后创建订单。
- 服务端重新验证价格，不信任前端传入金额。
- 防止重复提交、越权读取、重复状态流转。
- 创建订单后，用户能够查看订单详情和状态。
- 所有关键数据真实保存到 PostgreSQL。
- 暂不接入真实支付；未收款订单不得伪装成已支付。

### 3. 客服工作台

- 客服登录。
- 查看其有权限处理的订单。
- 接单、处理、更新订单状态。
- 能够查看必要的用户订单信息。
- 对不合法的状态跳转给出明确提示。
- 保留必要的操作审计记录。

### 4. 管理员后台

- 管理商品和规格。
- 查看订单与处理状态。
- 管理客服账号和权限。
- 管理订单异常情况。
- 防止普通用户绕过前端直接调用管理员接口。

## 三、真实业务测试

使用 Playwright，在私有 Staging 中完整模拟：

1. 注册测试用户。
2. 登录账号。
3. 浏览商品并选择规格。
4. 提交订单。
5. 刷新页面，确认订单仍然存在。
6. 客服登录并处理订单。
7. 用户重新查看订单状态。
8. 管理员登录并查看订单记录。
9. 验证未授权用户无法查看其他人的订单。
10. 验证服务重启后数据仍然存在。

同时补充单元测试、接口测试、数据库一致性测试。

不得只靠 Mock 数据证明流程正常。
