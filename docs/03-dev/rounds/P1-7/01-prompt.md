## 一、Goal

1. **让老板（下单用户）在自己的页面看到五项本人统计数据**：
   累计订单数 / 累计消费金额 / 最近 30 天消费 / 常玩游戏 / 常用打手。
2. **把三处消费金额统计收敛到唯一口径**：
   累计消费（`/mine` 面板）· 消费等级（`/api/me/consumption-level`）· 用户消费排行榜
   都走同一个纯函数 `effectiveSpend = max(0, actualPaidAmount − refundedAmount)`。

## 二、为什么是这两件事一起做

它们**不是两件事**。`P1 | 老板数据 | 累计消费金额` 这一行早就存在（以「消费等级卡」的形态），
而权威文档里它一直挂着一个 `⏳`：

- `docs/01-requirements/超哥电竞_业务流程表.md` §19 消费累计：
  「消费累计按 `actualPaidAmount` 增加。退款以后：**按真实退款金额回滚消费累计**。
  状态：旧实现有基础；**真实金额回滚 ⏳**」
- `docs/02-tech-design/database-schema.md` §16 把它记成 TARGET：
  `Σ max(0, actualPaidAmount − refundedAmount)`，**未实现**。

也就是说：**给老板显示一个金额，前提是先定义清楚这个金额是什么。**
所以面板与口径必须同轮交付。`F1` 就是那个 `⏳` 的兑现。

## 五、开发纪律（本轮实际遵守的）

1. **统计全部在服务端**；React 组件**不遍历订单、不做任何聚合**。
2. **金额一律为整数分**；展示层复用既有 `formatYuan`，不另造格式。
3. **退款联动只有一条链**；不出现第二份 `actualPaidAmount − refundedAmount`。
4. **DTO 最小化**：聚合结果，不是订单列表——不含 `orderId` / `orderNo` / `remark` 等明细。
5. **只有当前用户能读自己的老板数据**：`userId` 只来自服务端会话，接口不接受任何「查谁」的参数。
6. **本轮不可点击**：面板是历史统计展示，不是「再来一单」入口（`D9` / `D11`）。
7. **修测试的红只允许一种方式**：改对实现。**禁止**通过 `skip` / 删除断言 / 放宽 exact key /
   增加 retry / 修改业务口径来让测试变绿。
8. **零 Git 写操作**：`git add` / `commit` / `push` / `reset` / `restore` / `checkout` / `rebase` / `amend`
   全程禁止；改动全部保留在工作区，由用户自行处理。
