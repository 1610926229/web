## 一、验收前置

```bash
pnpm dev            # :3000
```

1. 打开 `http://localhost:3000/admin`，用**模拟管理员登录**进入后台。
2. 左侧导航最后一段应能看到新条目 **「售后工作台」**（在「投诉处理」之后、「客服账号」之前）。
   ⚠️ 既有的「退款审核」与「投诉处理」**两条入口必须仍然在**——本轮的聚合入口**没有**替换它们。
3. 数据来自 `globalThis` mock store，**重启开发服务器会回到预置数据**。
   下面的数字都按**预置数据**给出（本轮交付时实测）。

### 预置数据的基准数字（验收时用来对数）

| 视图 | 角标 / 条数 |
|---|---|
| 全部 | 12 |
| 未完结 | **7** |
| 处理中 | 3 |
| 已结束 | 5 |

⚠️ **注意 7 + 3 + 5 ≠ 12，这是有意的**：`处理中` 是 `未完结` 里**已经有人接手的那一部分**，
两者**重叠**。正确关系是 `全部 = 未完结 + 已结束`（7 + 5 = 12）且 `处理中 ⊆ 未完结`。
页面上那句说明就是这么写的，**不是 bug**。

## 二、验收步骤

### A. 列表与三视图

| # | 操作 | 预期 |
|---|---|---|
| A1 | 进入 `/admin/aftersales` | 默认落在 **「未完结」** 页签；顶部说明文字可见；列表按**提交时间倒序** |
| A2 | 看四个页签的角标 | `全部 12 · 未完结 7 · 处理中 3 · 已结束 5` |
| 🔴 A3 | 停在「未完结」，逐行看状态列 | **必须同时出现**：`待审核` 退款、**`审核中` 退款**、`待处理` 投诉、**`处理中` 投诉**。 ⚠️ 若「审核中」的退款**不在**「未完结」里，说明 **BLOCKER-1 回退了**，请立刻记录 |
| 🔴 A4 | 切到「处理中」 | 只剩 `审核中` 退款与 `处理中` 投诉（**不含**任何 `待审核` / `待处理`，也**不含**已结束的） |
| A5 | 切到「已结束」 | 只剩终态：`已拒绝` / `已通过` / `已撤销` 退款、`已处理` / `已关闭` 投诉 |
| A6 | 切到「全部」 | 12 条，含三类 |
| 🔴 A7 | 停在任意一个页签，比较四个角标 | **四个数字必须完全一样**（角标**不随**当前页签变化）。 切到「未完结」后「处理中」**不能**变成 0 |
| A8 | 点「下一页」/ 看分页信息 | 总数与当前页签的条数一致；翻页不重不漏 |

### F. 四态（loading / error / retry / empty）

⚠️ 以下 mock 参数都需要 `.env.local` 里 `ENABLE_MOCK_DEBUG=true`；关掉开关时它们**全部失效**（静默直通，不报错）。

⚠️ **本页有两个不同的错误态，别混淆**——`?mockError=1` 打挂**整块内容区**（页面级），
`?mockError=api` 只打挂**浏览器端请求**（表格局部，筛选栏与左侧导航都还在）：

| # | 操作 | 预期 |
|---|---|---|
| F1 | 首次进入页面 | 有加载骨架（`loading.tsx`） |
| F2 | `?mockEmpty=aftersales` | 空态文案 + 重置筛选按钮；**四个角标一并归零**（`全部 0 · 未完结 0 · 处理中 0 · 已结束 0`） |
| F3 | `?mockEmpty=refunds` 或 `=complaints` | 工作台**不受影响**（它是独立取数入口）—— 反过来验证 F2 的清空范围没串味 |
| 🔴 F4 | `?mockError=1` | **整块内容区**变成错误态；左侧导航**仍然在**（错误边界只罩内容区）；点**「重试」**应能恢复—— 重试会先把调试参数摘掉再重新请求 |
| 🔴 F5 | `?mockError=api` | 页面**正常渲染**（服务端侧不受影响）。再点一次「查询」或改任一筛选 → **表格局部**错误态 + 「重试」，**筛选栏与导航都还在** |
| F6 | 断网后点「查询」 | 同 F5 |

> ⚠️ **F5 必须有一次交互才会出现**：首屏用的是服务端已取好的数据，客户端**不会**在挂载时重取。
> 直接盯着首屏看不到局部错误态，别误判成「没生效」。

## 五、如实登记的缺口与已知边界（**验收时请一并知悉**）

这一节列的**不是**「没做完」，是「**明确不覆盖**或**依赖别处**」，写清楚以免被误读成已覆盖。

1. **cmd 第 7 条（一单一退不回归）**：本文件不直接断言。理由——工作台**只读**，
   接口只有 `GET`、不 import 任何 `*Transaction.ts`，因此**结构上不可能改坏**一单一退；
   该规则由 P0-15 的既有套件守着（全量 0 fail）。
2. **cmd 第 8 条（partial/full）只覆盖了一半**：种子数据里**不存在**「已批准且比例 < 100%」的
   部分退款，因此「部分退款**不**强制 `Order.status = refunded`」这条**没有直接断言**——
   只断言了「全额 ⇒ `refunded`」与「非 approved ⇒ 不是 `refunded`」。
   **没有为了让断言好看而放宽或伪造种子。**
3. **cmd 第 9 条（approved 后打手收益为 0）**：工作台的行 DTO **刻意不含** earning 字段
   （D-P1-3-9 的最小化口径），因此这一条**在本文件里无落点**，由 P0-15 的既有套件承担。
4. **cmd 第 10 条（Staff 调查历史）**：**客服会话**有真样本、已断言可达且不另造；
   但**履约退出历史**在本项目的预置数据里**为空表**（`mockCompanionReleaseRepository.ts` 明写
   「只增不改的历史表，建仓时是空的」，种子注释也写明「没有任何一位打手退出过」），
   因此只断言了它**是数组且与直接取详情深等**（守「透传、不另造」），**没有**断言「有内容」。
5. **「guard 先于解析」这条断言没有红-绿证据**：要证伪它必须把 `requireAdmin()` 临时挪到解析之后，
   而仓库既有安全约定**禁止为红绿验证摘鉴权守卫**，该注入被安全策略拒绝。
   判别力来自结构断言（handler 的第一个 `await` 必须**恰好是** `await requireAdmin()`），
   **已知缺口、不补、如实登记**。
6. **两个专用页的正文等价**：抽取成 `Admin*Sections` 时做过**抽取当场**的三 URL 字节级 HTML 比对
   （区块文本 8/8 与 7/7 逐字相同）。但**事后**复核只能对齐到 `HEAD`——工作区同时含
   P0-14 / P0-15 的未提交改动，无法还原「P1-3 前一刻」的快照。复核比对结果是
   label / 标题全部一致、无无法解释的内容丢失，但**这条证据的强度低于当场那次比对**。
7. **`loading` / `retry` 无自动化覆盖**：组件行为，Node 24 不剥 JSX。见 §二-F 手工步骤。
8. **页面尺寸**：本页是**管理后台**（PC），沿用既有后台设计体系，**不是**移动端 H5 页面。
