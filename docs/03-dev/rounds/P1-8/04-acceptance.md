```bash

ENABLE_MOCK_AUTH=true ENABLE_MOCK_DEBUG=true ENABLE_MOCK_ADMIN=true pnpm dev        # :3000

# 或按门禁用的生产构建（本文档所有数字都在这个构建上复算过）

  && ENABLE_MOCK_AUTH=true ENABLE_MOCK_DEBUG=true ENABLE_MOCK_ADMIN=true \
     pnpm exec next start -p 3105
```

| 开关 | 为什么必须 |
|---|---|
| `ENABLE_MOCK_AUTH=true` | **必须**。没有它就没有模拟登录 / 切换身份入口，用户端会停在登录闸门上 |
| `ENABLE_MOCK_ADMIN=true` | **必须**。没有它 `/api/admin/auth/mock-login` 不存在，进不了管理后台 |
| `ENABLE_MOCK_DEBUG=true` | 只有 §I（空态注入 / 故障注入）需要 |

> ⚠️ **验收前请重启服务。** 带 `APP_BASE_URL` 跑 `pnpm test` 会**真的改动这个服务的
> `globalThis` 存储**（HTTP 用例会真的提交评价、真的审核、真的退款）。
> 本文档 §一 的表格是「**刚起服务**」的值。若你先跑了全量测试再来看，数字会对不上——
> **那不是 bug，是内存态被测试写脏了**。重启即可复原。

## 二、验收清单

> 每条给：**怎么做** → **应该看到什么**。带 ⚠️ 的是最容易出错的点。

### A · 公开面：评分与评价数真的来自评价记录（`D17` / `D14` / `D15`）

**A1 · 打手详情的分数与条数**

1. 以任意身份（甚至未登录）打开 `/companions/cp-1`；
2. 应该看到 **4.7 分**、以及评价区里的 **3 条**评价。

⚠️ **重点核对「4.7」这个数**：它在 `P1-8` 之前**也是 4.7**（种子里写死的）。
所以「看到 4.7」**不能**证明聚合生效。真正能证明的是下面 A2/A3——**改动一条评价的状态，分数立刻跟着变**。

**A2 · 隐藏一条评价，分数与条数立刻下降**

1. 管理员登录 → `/admin/reviews`；
2. 找到 `rev-seed-1003-01`（作者「星**」，打手 `cp-1`，5 分），点**隐藏**，填原因（随便写，比如「验收演示」）；
3. 回到 `/companions/cp-1`（刷新）；
4. 应该看到：**评价数 3 → 2**，**平均分 4.7 → 4.5**（只剩 5 + 4 = 9 ÷ 2 = 4.5），且那条评价**从列表里消失**。

⚠️ 这是本轮的**核心可见证据**：分数不再来自任何静态字段，而是**每次读取现算**。

**A3 · 恢复公开，分数与条数加回来**

1. 在 `/admin/reviews` 找到刚才那条（筛「已隐藏」），点**恢复公开**；
2. 回到 `/companions/cp-1`；
3. 应该看到 **4.7 / 3 条**，评价**回到列表里**。

**A4 · 最近 3 条截断**

1. 打开 `/companions/cp-3`；
2. 应该看到 **4.5 分**、**「4 条评价」**，但列表里**只有 3 条**。

⚠️ 「条数写 4、列表只有 3 条」**不是 bug**：条数是维度总数，列表按 `D15` 只给最近 3 条。

**A5 · 暂无评分 ≠ 0 分**

1. 打开 `/companions/cp-8`（或 `/product/p-fun-2`）；
2. 应该看到 **「暂无评分」**，**不是「0.0」**。

⚠️ 文案与数字都要看：`0.0` 表示**真的被打了 0 分**，是一件不同的事（`D15`）。

**A6 · 商品侧与打手侧**同源

1. 打开 `/product/p-400w` → 应显示「暂无评分」（因为它**没有商品维度**）；
2. 打开 `/companions/cp-3` → 那条评了 `cp-3` 但没评商品的评价**应该在**（若在最近 3 条内），且 `cp-3` 的 4.5 分里**含它的 5 分**。

⚠️ 详见 §1.3 ①。这是 `R4`（`productId` 是**维度身份**不是**评价身份**）唯一能用手确认的地方。

### C · 审核状态机：四个动作（`D7` / `D10` / `D11` / `D12`）

**C1 · 驳回必须填原因**

1. 管理员在 `/admin/reviews` 对一条 `pending`（比如 `rev-seed-1004-02`）点**驳回**；
2. **原因留空** → 应被**拒绝**（前端拦住或服务端 400）；
3. 原因只填空格 → 同样应被拒绝。

⚠️ 「只填空格」这一次**一定要试**：`trim` 之后为空必须算没填（`D10`）。

**C2 · 驳回之后作者看到什么**

1. 填上原因（比如「描述与实际不符，请补充说明」）提交驳回；
2. 以 `u-1004` 打开 `/reviews`；
3. 应看到 **「已驳回」** 状态标签 + **你刚写的原因** + 一个 **「重新提交」** 入口。

**C3 · 重新提交是**同一条**，不是第二条**

1. 以 `u-1004` 从 C2 点「重新提交」，改一下正文（或星级），提交；
2. 回 `/admin/reviews`（筛「待审核」）→ **应该只有一条**（`rev-seed-1004-02`），**状态回到 `pending`**；
3. ⚠️ **不应该出现两条**——若出现第二条，说明「重新提交」被实现成了「新建」。

**C4 · 状态机外的动作被拒绝，且提示该用哪个**

1. 把 C3 那条**通过**；
2. 对这条**已通过**的评价点**「驳回」**；
3. 应**被拒绝**，且提示**应改用「隐藏」**（而不是一句「操作失败」）。

⚠️ 提示文案要能让人知道**下一步该点哪个按钮**（`D10`）。

**C5 · 隐藏 → 恢复公开**

1. 对一条 `approved` 点**隐藏**，填原因 → 应成功；
2. 再对这条（现在 `hidden`）点**「恢复公开」** → 应**不需要填原因**就能成功；
3. 回公开面 → 分数与条数**恢复**（与 A3 同）。

**C6 · 管理员改不了内容（`D12`）**

1. 用浏览器开发者工具，对审核接口**手工构造一个**带上 `content` / `rating` / `productReview` 的请求体；
2. 发出去；
3. 回公开面看 → **内容和星级一个字都没变**，只有**状态**变了。

⚠️ 服务端**根本不读**这些键——不是「读了但忽略」，是**根本没有这条代码路径**。

**C7 · 四个动作是四个地址**

1. 在浏览器 Network 面板看四个动作分别打到哪；
2. 应该是 `/api/admin/reviews/<id>/approve` · `/reject` · `/hide` · `/unhide` **四个不同的 URL**，**不是** `PATCH .../reviews/<id>` 带 `{action}`。

⚠️ 为什么要这样：审计的动作名直接取自 URL。若用一个 `PATCH` 带 `{action}`，
审计就得**再从请求体里解析一次动作名**——而请求体是调用方可以写错的，URL 不是。

**C8 · （已知行为，验收时请判断是否符合预期）对**已经**被驳回的评价再点一次「驳回」**

1. 对一条已经是「已驳回」的评价，再点一次**驳回**，并且**改填一个不同的原因**；
2. 接口返回**成功**（`200`），但：
   - `changed` 是 `false`（什么也没改）；
   - **驳回原因仍然是第一次那条**，新填的原因**不会被写进去**；
   - **不产生**第二条审计。

⚠️ **这是刻意的**：`P1-8` 冻结的状态机（`D7`）里**没有** `rejected → rejected` 这条边，
所以「再驳一次」不是一次合法迁移；把对「已是目标状态」的重复操作当成**空操作**，
与本仓既有的「启停」类接口口径一致。

⚠️ **请验收确认**：如果产品**需要**「重新驳回以更换原因」这个能力，那是一条**新裁定**
（要么新增一个动作，要么显式允许这条迁移），需要另行提出——本轮**没有**自行发明。
详见 `05-review.md` §三 `N1`。

### D · 审计（`D22`）

**D1 · 每个动作都留痕**

1. 连着做：通过一条、驳回一条、隐藏一条、恢复公开一条；
2. 核对审计（管理员账号下可见的审计列表，或在后台「操作日志」处）：
   应该有 **`review.approve` / `review.reject` / `review.hide` / `review.unhide` 各一条**。

⚠️ **`恢复公开` 也要有**：不填原因不代表不记账（`D10`/`D11`）。

**D2 · 审计能回答「谁 / 哪条 / 什么动作 / 何时 / 为什么」**

1. 逐条看审计内容；
2. 应能看出**操作人**、**是哪条评价**、**做了什么**、**时间**、以及**驳回/隐藏的原因**。

**D3 · 空操作不写第二条**

1. 对一条**已经是 `approved`** 的再点一次**通过**；
2. 审计**不应多出一条**（没有状态变化就没有审计）。

**D4 · 审计里没有用户隐私**

1. 检查审计记录里存的内容；
2. **不应**出现用户昵称以外的隐私字段（手机号 / 微信 ID / 平台 ID）。

### E · 退款与评价是两条线（`D18` / `D19` / `D20`）

> 这四条要用管理员在订单侧真的发起退款。**建议每做完一条就重启服务**，
> 因为「一单一退」（`P0-15`）会让一张单**退过一次之后就再也退不动**。

**E1 · 已完成之后，部分退款仍然可以评价**

1. 找一张 `completed` 且**未评价**的订单，管理员发起**部分退款**（比如退 30%）；
2. 以该用户打开订单详情 → 评价入口**应该还在**（「去评价」）；
3. 提交评价 → **应成功**。

**E2 · 已完成之后，**全额**退款**仍**可以评价**

1. 另一张 `completed` 且未评价的订单，管理员发起**全额**退款（订单状态会变成 `refunded`）；
2. 以该用户打开订单详情 → 评价入口**应该还在**。

⚠️ 这是本轮最反直觉的一条（`D19`）：**判据是 `completedAt` 这个事实，不是当前状态名**。
全额退款**不会**抹掉 `completedAt`。

**E3 · 完成前退款 → 不能评价**

1. 找一张 `paid` 或 `accepted`（**还没完成**）的订单，管理员退款；
2. 以该用户打开订单详情；
3. 评价入口**应该没有了**（或明确提示不可评价）。

⚠️ E2 与 E3 的对照就是 `D19` 的全部内容：**同样都是「已退款」，一条能评一条不能**。

**E4 · 评价通过之后再退款，评价**不**被自动撤下**

1. 先给一张已完成订单提交评价，管理员**通过**它；
2. 记下当时的公开面（商品页 / 打手页）分数与条数；
3. 现在对这张订单发起退款（部分或全额都行）；
4. 回公开面 → **评价应该还在**，分数与条数**不变**。

⚠️ **这是 `D20` 的验收点，也是最容易实现错的一条**：
若退款之后评价**消失**了，说明有人把退款**偷偷映射成了 `approved → hidden`**——
那在审计里会留下一条**看起来像是管理员手动隐藏的**记录，而**没有任何管理员做过这个决定**。

**E5 · 想撤下只能显式隐藏**

1. 在 E4 之后，管理员对那条评价点**隐藏**；
2. 公开面**这时才**去掉它，且审计里留下 **`review.hide`** + 原因。

### H · 订单详情 / 我的评价：六个状态都对

| 状态 | 看到什么 | 种子样本 |
|---|---|---|
| 未评价 | **「去评价」** | `ord-seed-1001-08` |
| `pending` | **「审核中」** | `rev-seed-1004-02`（作者 `u-1004`） |
| `approved` | **「已通过」** | 上面 §1.4 的 9 条 |
| `rejected` | **「已驳回」** + 原因 + **「重新提交」** | **无预置**，用 §C1/C2 现场造 |
| `hidden` | **「已隐藏」** + 「已被管理员隐藏」+ 隐藏原因 | `rev-seed-1008-01`（作者 `u-1008`） |
| 不可评价 | **没有入口** | 完成前退款的单（§E3 现场造） |

⚠️ **`hidden` 那条要特别看**（`D8`）：作者看到的应该是
**「已被管理员隐藏」+ 隐藏原因**，而**不是**一个和「审核中」长得一样的标签。
若作者根本看不出它被隐藏了，作者会以为**自己提交失败了**。
