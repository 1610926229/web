# P1-8 · 本轮章程

> 本文档是 `P1-8` 的**轮次章程**：范围、判据、纪律。
> 2026-10-02 建立。**内容整理自本轮实际执行的指令与 `02-decisions.md` 的取证**，
> 不是事后追认的新要求——每一条都对应本轮真实做过（或明确没做）的决定。

---

## 一、Goal

把**订单评价**从「能写一条记录」做成一个**闭环**：

1. **双维度评价**——一份评价同时覆盖「本单商品」与「本单实际服务打手」，
   两个维度各有独立星级与独立正文（`D1`–`D3`）；
2. **审核闸门**——提交后**不是终态**，先进 `pending`，管理员 `approve` 之后才公开（`D7`）；
3. **公开面由真实评价算出来**——商品详情与打手详情的平均分 / 评价数 / 最近评价
   全部来自 `approved` 的 `OrderReview`，**种子里那份静态假分数彻底退出业务真值**（`D17`）。

## 二、为什么这三件事必须一起做

它们**不是三件事**，拆开每一件都会留下一个自相矛盾的状态：

| 只做其中一件 | 会留下什么 |
|---|---|
| 只做双维度，不做审核 | 提交即公开。那今天的行为**立刻变成**「一提交就上墙」，与「审核后才公开」直接冲突 |
| 只做审核，不做双维度 | 审核的对象还是**一份合并的星级**。管理员没法回答「驳回的是商品评价还是打手评价」 |
| 只做公开面，不动作 | 用户看到的是**伪造的**平均分与评价（种子里写死的），而真实评价已经在库里——同一页上两个真值 |

第三条尤其关键：`P1-8` 之前，打手详情的评分来自 `companionSeed` 里写死的
`rating = 4.7` / `reviewCount = 3` / 内嵌 `reviews[]`。那一份数据**看起来完全正常**，
差别只在「有没有人去核对它和评价记录对不对得上」。
因此本轮不只是「补一个聚合」——必须**删掉那份静态真值**，让页面上只剩一个来源。

## 三、本轮**不做**什么

| 不做 | 为什么 |
|---|---|
| 完整评价列表页（商品侧 / 打手侧） | `D16` 明确不做。详情页的「最近 3 条」已经覆盖浏览需求 |
| 打手端 / 客服端的评价表面 | `D21` 给的是**上限不是下限**。打手端现在没有评价这项业务，建一个只读表面会凭空多出一个要长期维护权限、却没有使用场景的界面（详见 `README.md` §5.4） |
| 评价回复、点赞、图片以外的新凭证类型 | 不在裁定范围内 |
| 让管理员编辑评价内容 | `D12` 明文禁止。管理员是**发布闸门**，不是编辑 |
| 退款自动撤下已通过的评价 | `D20` 明文禁止。退款与评价是两条互不干涉的线 |
| 「服务是否完成」的新业务状态 | `D19` 明文要求以 `completedAt` 这个**既有事实**为判据，不新增状态 |

## 四、判据（本轮做完的标志）

1. 一单一条逻辑评价，最多两个维度，至少一个有效维度（`R1`、`D3`）；
2. 四个状态与五条迁移严格按 `D7`，**不复用 `Order.status`**；
3. `approve` / `reject` / `hide` / `unhide` 四个动作全部进 `AdminAudit`（`D22`）；
4. 商品侧与打手侧的聚合**同源**（`R3`）：唯一入口 `lib/services/reviewAggregates.ts`；
5. 只有完成过服务的订单可以评价，**与退款无关**（`D18`/`D19`/`D20`）；
6. 权限在**服务端**强制（`D21`），不是靠隐藏按钮；
7. 门禁全绿，停在 `AWAITING_ACCEPTANCE`。

## 五、纪律

- **禁止任何 Git 写操作**：`add` / `commit` / `push` / `reset` / `restore` / `checkout` /
  `rebase` / `amend` 全程未执行。
- **不得删除断言、`skip`、`retry` 或放宽业务要求。** 与裁定冲突的旧断言
  **改写成守住裁定之后的规则**，不是删掉。
- **不得自行标记 `DONE`。** 本轮终点是 `AWAITING_ACCEPTANCE`。
- 纯工程问题（落点、命名、目录结构）由 Claude 自行决定，不上交产品。
- 与裁定冲突时**一律以裁定为准**；裁定本身不得自行更改。
