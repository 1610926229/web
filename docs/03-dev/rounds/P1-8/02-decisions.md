## 组 A · 评价对象与结构

### D1 · 一份评价是否同时评价「商品 + 打手」

1. **问题**：一笔订单的评价，是**一份**同时覆盖商品与打手，还是**两份各自独立的评价记录**？
2. **当前代码事实**：**一份**。`OrderReview` 只有一组 `rating` + `content`，同时挂着商品快照与打手快照。
3. **原需求事实**：产品目标 3「评价对象包括：本单商品、本单实际服务打手」——**说了两个对象**，但**没说是一份还是两份**。
4. **选项**：(a) 一份记录含双维度；(b) 两份记录（各自独立实体、各自独立一单一次）。
5. **推荐**：(a)。理由：用户侧只有**一次提交动作**（目标 2「一次订单最多评价一次」是对**一次提交**说的），两份记录会让「一单一次」的唯一键含义变模糊。
6. **业务差异**：影响唯一键设计、审核粒度（能否只放行商品评价、驳回打手评价）、以及「已评价」的判定。**(b) 会让「同一单只评了商品没评打手」成为合法中间态。**
7. **判定**：🔴 **BLOCKING**（决定数据模型与唯一键）。

### D2 · 商品与打手是否各自有独立星级与独立文本

1. **问题**：如果 D1 选 (a)，商品与打手是**各自一个星级 + 各自一段文本**，还是**共用同一个星级和同一段文本**？
2. **当前代码事实**：**共用一份**。没有 `productRating` / `productContent` / `companionRating` / `companionContent`（全仓 0 命中）。
3. **原需求事实**：目标 3 说「评价对象包括商品 + 打手」；**未说明**星级与文本是否分开。
4. **选项**：(a) 各自独立星级 + 独立文本；(b) 一个总星级 + 一段总文本；(c) 独立星级、共用一段文本。
5. **推荐**：(a)。理由：两个对象是可独立打分的主体，平均分要分别聚合成商品分与打手分；共用一份会让「商品 4 星但打手 1 星」无法表达。
6. **业务差异**：直接决定平均分口径与表单复杂度。若选 (b)，则商品/打手两侧**不可能有独立平均分**，D14/D15 失去意义。
7. **判定**：🔴 **BLOCKING**。

### D3 · 是否允许只评其中一个

1. **问题**：用户能否**只评商品不评打手**（或反之）？
2. **当前代码事实**：不存在「部分评价」——一次提交必须同时给出唯一的星级与正文。
3. **原需求事实**：未定义。
4. **选项**：(a) 必须两个都评；(b) 至少评一个；(c) 两个都可选（允许纯文本无星级）。
5. **推荐**：(a)。理由：「一单一次」最容易守住；若允许部分提交，需定义「提交到一半」的状态与是否算「已评价」（会直接改变 D9 的答案）。
6. **业务差异**：若允许部分评价，则「已评价」不再是布尔值，而是「商品已评 / 打手已评」两个位 ⇒ 唯一键、角标、入口显示全部要改。
7. **判定**：🔴 **BLOCKING**。

### D4 · 打手维度评的是谁

1. **问题**：打手维度评价的，是**最终实际履约的那位**（`Order.actualCompanionId`），还是**本单所有曾进入过 `serving` 的打手**（一单多评）？
2. **当前代码事实**：只记录**一位**——`order.companion`（= `actualCompanionId` 的快照，`lib/types/order.ts:250-258` 明写两者同一段原子代码写入）。**用户当初指定的是 `exclusiveCompanionId`，是完全不同的字段**。
3. **原需求事实**：目标 3 写的是「本单**实际服务**打手」（单数），倾向于「实际履约的那位」；**但未说明换人后是否要给曾经服务过的人也留评价**。
4. **选项**：(a) 只评最终 `actualCompanionId`；(b) 每位曾 `serving` 的打手各可得一条评价。
5. **推荐**：(a)。理由：与 `P1-7` 的 `D7`/`D8` 口径一致——打手的「服务次数」按**真实进入过 `serving`** 计，但**评价**是对「这次服务体验」的表态，用户只体验了完整一单；且 (b) 会让「一单一次」变成「一单 N 次」，与目标 2 冲突。
6. **业务差异**：(b) 会让 A→B 的订单产生 2 条评价，打手平均分的分母随之变化；也会让「一单一评」的唯一键必须从 `(userId, orderId)` 变成 `(userId, orderId, companionId)`。
7. **判定**：🔴 **BLOCKING**。

### D5 · 客服换人 / A→B 场景下 A 是否可得评价

1. **问题**：客服换人后（A 服务过一段，B 接手完成），A 该不该被评价？如果该，什么时候评？
2. **当前代码事实**：**A 不可能被评价**——`Order.actualCompanionId` 在换人时被改写为 B，订单完成时快照里只有 B。`CompanionReleaseRecord`（`lib/data/mockCompanionReleaseRepository.ts`）记的是「谁走了」，但**评价链路完全不读它**。`P1-7` 的 `CompanionServiceEvent` 记录了每位真实服务过的打手（`(orderId, companionId, servingAt)`），**评价链路同样不读**。
3. **原需求事实**：未定义。`P0-11` 只裁定了「换人不设次数上限」；`P1-7` 裁定 `CompanionServiceEvent` **不承担**跨域 Assignment identity。
4. **选项**：(a) A 不可被评价（只有完成者可得）；(b) A 可由客服/管理员补评（走别的通道）；(c) A 由用户在完成后一并评价（一单多评，与 D4(b) 绑定）。
5. **推荐**：(a)。理由：与 D4 推荐一致；且「A 被换走」这件事本身通常已由客服介入处理，不需要再引入一条评价通道。
6. **业务差异**：若选 (b)/(c)，需要新的入口、新的权限、以及「一单多评」的模型改造；打手平均分口径也会随之变化。
7. **判定**：🔴 **BLOCKING**（与 D4 联动）。

## 组 B · 审核与可见性

### D6 · 「公开」的落点在哪里

1. **问题**：审核通过后，评价**具体出现在哪些页面**、对**谁**可见？
2. **当前代码事实**：**没有任何公开读路径**。评价只出现在：作者本人的「我的评价」、作者本人的订单详情摘要、管理端订单详情一行只读。商品详情**没有**评价区块；打手详情的评价来自**静态种子**。
3. **原需求事实**：目标 5/6 只说「不是立即公开、审核后才允许公开」，**没说公开在哪里**。
4. **选项**：(a) 商品详情；(b) 打手详情；(c) 两者都上；(d) 另有独立的评价广场/列表页。
5. **推荐**：(c)。理由：产品目标 3 把「商品」与「打手」并列为评价对象，公开面应与评价对象一一对应；(d) 原型里没有，不建议新造。
6. **业务差异**：决定要不要给 `OrderReview` 补 `productId`（当前**没有**，见 README §4）、以及打手详情的静态评分要怎么处理（见 D17）。**这是本轮体量最大的一个决定。**
7. **判定**：🔴 **BLOCKING**。

### D7 · 审核状态模型

1. **问题**：评价的状态机长什么样？
2. **当前代码事实**：**没有状态字段**。`OrderReview` 写入即终态。`grep ReviewStatus` 全仓 0 命中。
3. **原需求事实**：目标 5（提交后不立即公开）+ 目标 6（管理员审核后才公开）+ 目标 7（管理员可隐藏**已公开**评价）——**至少隐含 4 个状态**：待审核 / 已公开 / 已驳回 / 已隐藏。**是否还需要「已下架 / 已删除」等额外状态未定义。**
4. **选项**：(a) 恰好四态 `pending / approved / rejected / hidden`；(b) 四态 + 额外终态；(c) 用「可见性 boolean + 审核结论」两个正交字段。
5. **推荐**：(a)。理由：与用户列出的四个词一一对应，不留未定义角落；`hidden` 与 `rejected` **语义不同**（前者是「曾是公开评价，管理员后来隐藏」，后者是「从未通过审核」），必须分开。
6. **业务差异**：状态模型决定审核列表的筛选维度、平均分口径（D14）、以及用户侧显示什么（D8）。
7. **判定**：🔴 **BLOCKING**。

### D8 · 待审核 / 驳回时作者本人是否可见

1. **问题**：评价还**没通过审核**（`pending`）或被**驳回**（`rejected`）时，**写它的用户本人**能不能在自己的「我的评价」里看到？
2. **当前代码事实**：不存在这个区分——提交后作者立刻在 `/reviews` 看得到（因为根本没有审核）。`/reviews` 的「已评价」Tab 读的是全部 `OrderReview`。
3. **原需求事实**：目标 5 说「提交后不是立即公开」；**「公开」是否包含「对作者本人可见」未定义**。
4. **选项**：(a) 作者始终可见（带状态标识）；(b) `pending` 可见、`rejected` 不可见；(c) 只有 `approved` 才进作者的列表。
5. **推荐**：(a)。理由：「不公开」约束的是**他人可见性**，不是作者自己的记录；且 (c) 会造成「我明明评价了，列表里却没有」的困惑，还会让「已评价」判定与服务端不一致。
6. **业务差异**：影响 `/reviews` 列表的过滤条件、Tab 角标（`counts.reviewed`）、以及订单详情里 `reviewSummary` 是否显示。
7. **判定**：🔴 **BLOCKING**。

### D9 · `reject` 后用户能否重新提交

1. **问题**：评价被驳回后，这一单还能再评一次吗？
2. **当前代码事实**：**没有驳回概念**，因此没有答案。现行约束是**彻底的一单一评**：业务唯一键 `${userId}:${orderId}`，命中即返回第一次的结果（`lib/services/reviews.ts:309-310`）。
3. **原需求事实**：目标 2 说「一次订单最多评价一次」；目标 4 说「提交后不可修改」。**「驳回后能否重提」与这两条都有张力**（重提既是「第二次评价」也是「修改」）。
4. **选项**：(a) 不可重提（真正的一次机会）；(b) 可重提，**覆盖**原记录；(c) 可重提，**新建**一条并保留被驳回的那条历史。
5. **推荐**：(b)，且**仅在 `rejected` 状态下**允许。理由：「驳回」的本意是「这次不行，改改再来」；若 (a)，管理员一次误判就永久剥夺了用户的评价权。⚠️ 但 (b) 与目标 4「提交后不可修改」有**字面冲突**，**必须由产品负责人确认目标 4 是否只约束「审核通过的/未被驳回的」提交**。
6. **业务差异**：(a) 与 (b)/(c) 会让唯一键语义完全不同；(c) 还要定义平均分取哪一条。**这一条同时会改变 D3/D8 的前提。**
7. **判定**：🔴 **BLOCKING**。

### D10 · `reject` / `hide` 是否必须填写原因

1. **问题**：管理员驳回或隐藏一条评价时，是否**强制**填写原因？
2. **当前代码事实**：**不存在**这两个动作，因此没有原因字段。
3. **原需求事实**：未定义。
4. **选项**：(a) 都必填；(b) 都可选；(c) 驳回必填、隐藏可选（或反之）。
5. **推荐**：(a)。理由：本仓已有先例——退款审核（`refund.reviewNote`）与入驻审核（`application.reviewNote`）都有审核备注，并通过 `AdminAudit` 留痕；评价是同类的「管理员对用户内容的裁定」，应同口径。
6. **业务差异**：影响管理端表单、`AdminAudit` 快照字段、以及用户是否能看到被驳回的理由。
7. **判定**：🟡 **NON_BLOCKING**（可以在实现时按推荐先做，但若产品有想法，改起来便宜）。

### D11 · `hide` 能否重新公开

1. **问题**：被隐藏的评价，管理员能不能重新公开？
2. **当前代码事实**：无此功能。
3. **原需求事实**：目标 7 只说「管理员可以隐藏已公开评价」，**没说是否可逆**。
4. **选项**：(a) 可逆（`hidden ⇄ approved`）；(b) 单向（隐藏即终结）。
5. **推荐**：(a)。理由：不可逆的隐藏等于删除，而本仓对「删除」一贯从严（`P1-6` 明确「不提供硬删除」）。但**如果选 (b)，则必须在 `AdminAudit` 里把隐藏做成可追溯的终态**，并明确「隐藏 ≠ 删除，数据仍在」。
6. **业务差异**：影响状态机（是否允许 `hidden → approved` 迁移）、平均分是否会被「隐藏后再公开」二次影响（D14）。
7. **判定**：🟡 **NON_BLOCKING**。

### D12 · 管理员能否编辑评价内容

1. **问题**：管理员可以**改写**用户写的星级或正文吗？
2. **当前代码事实**：不存在。`OrderReview` 写入后没有任何修改路径。
3. **原需求事实**：**未定义**。目标 6/7 只给了「审核」与「隐藏」两个动作，**没有「编辑」**。
4. **选项**：(a) 不能编辑，只能通过/驳回/隐藏；(b) 可以编辑（等于管理员代笔）。
5. **推荐**：(a)。理由：用户的评价是**用户写的话**，`P1-2/03-delivery.md:241` 已就同类数据立过一条纪律（「这是用户当初写下的话，改它等于篡改数据」）。管理员不该有能力把 1 星改成 5 星。
6. **业务差异**：(b) 会让「评分」这一列不再可信，并使 `AdminAudit` 必须记录「谁把几星改成了几星」。
7. **判定**：🟡 **NON_BLOCKING**（推荐明确，且与既有纪律一致）。

### D13 · 是否允许匿名展示

1. **问题**：公开的评价是否显示评价者身份？用真名、昵称，还是匿名？
2. **当前代码事实**：**现在没有公开面，因此没有展示口径**。作者自己的列表里不显示作者名（只显示商品/打手）。打手详情的评价来自种子，显示的是**手写的 `nickname`**（`CompanionReview.nickname`，`lib/types/companion.ts:110-116`）。
3. **原需求事实**：未定义。
4. **选项**：(a) 显示脱敏昵称（如「李**」或用户昵称）；(b) 完全匿名（「匿名用户」）；(c) 显示用户头像 + 昵称。
5. **推荐**：(a)，并**沿用本仓既有的脱敏惯例**（`lib/utils` 里已有对手机号等的脱敏工具）。理由：纯匿名会削弱评价可信度，全量展示身份又与既有 DTO 最小化纪律冲突。
6. **业务差异**：决定公开 DTO 要不要带用户身份字段，以及是否需要新的脱敏函数。⚠️ **「匿名」还牵扯一个法律/合规问题**（评价者身份对商家不可见通常需要显式说明），若产品无明确答案，**不应由开发自行决定**。
7. **判定**：🟡 **NON_BLOCKING**（但若公开面（D6）本轮就要做，则升级为 🔴 —— 它决定公开 DTO 的形状）。

## 组 C · 聚合与展示

### D14 · 评价何时进入平均分

1. **问题**：平均分与评价数，从哪个状态开始计入？`pending` 算不算？`hidden` / `rejected` 要不要扣回？
2. **当前代码事实**：**没有真实聚合**。打手的 `rating` / `reviewCount` 是 `seed.ts` 里手写的；商品侧根本没有。
3. **原需求事实**：未定义。
4. **选项**：(a) 只有 `approved` 计入，`hidden` 立即扣回；(b) `pending` 也计入；(c) `approved` 与 `hidden` 都计入。
5. **推荐**：(a)。理由：目标 6 的「审核后才公开」如果平均分却在审核前就动，等于**提前公开了评价的存在与数值**，自相矛盾；(c) 会让「隐藏」这个动作失去意义。
6. **业务差异**：决定聚合函数的过滤条件，也决定审核动作是否要触发重算。**若选 (b)，公开页面会在审核前就暴露未审核评价的统计特征。**
7. **判定**：🔴 **BLOCKING**（与 D6/D7 联动）。

### D15 · 平均分精度 / 无评价显示 / 展示条数

1. **问题**：平均分保留几位？没有评价时显示什么？详情页显示多少条最近评价？
2. **当前代码事实**：打手侧**已有先例**——`companion.rating === null ? "暂无评分" : companion.rating.toFixed(1)`（`components/companions/CompanionDetailView.tsx:73`），即 **1 位小数 + 「暂无评分」不用 0 冒充**；详情页评价条数上限 `COMPANION_DETAIL_REVIEW_LIMIT = 3`（`lib/constants/companions.ts:36`），并给 `reviewsTruncated` 标识。商品侧无任何先例。
3. **原需求事实**：未定义。
4. **选项**：(a) 沿用打手侧既有口径（1 位小数 / 「暂无评分」/ 3 条）；(b) 另立一套。
5. **推荐**：(a)。理由：本仓对「同一件事不要两套口径」有强纪律（`R2` 的教训）；打手侧这套已经跑通且原型一致。
6. **业务差异**：若商品侧另立一套，会出现「同一个人在两个页面看到两种格式」。⚠️ 需要产品确认的是**条数**（3 条是否够）与**精度**（是否要 1 位）——这两项目前都只是**实现惯例**，不是裁定。
7. **判定**：🟡 **NON_BLOCKING**（推荐明确；但若产品对条数有想法，改起来便宜）。

### D18 · 部分退款后能否评价

1. **问题**：一笔订单被**部分退款**（10% / 50%）后，用户还能评价吗？
2. **当前代码事实**：**不能**。`canReviewOrder`（`lib/constants/reviews.ts:238-240`）只看 `refundStatus === "approved"`，**不区分比例**——部分退款与全额退款一视同仁，永久关闭评价入口，文案是「该订单已退款，无法评价」。
3. **原需求事实**：⚠️ **`docs/01-requirements/` 三个文件里 `评价` 命中数为 0 —— 产品从未定义过。** 这条是**代码自行推导的**，不是裁定。相关背景：`P0-15` 裁定「一单一退，管理员只输入退款比例；**只有比例 100% 才**把 `Order.status` 转 `refunded`」，即**部分退款后订单仍是 `completed`**。
4. **选项**：(a) 部分退款仍可评价（订单确实完成了服务）；(b) 任何退款都不可评价（维持现状）；(c) 只有全额不可评价，部分按比例阈值定。
5. **推荐**：(a)。理由：`P0-15` 明确部分退款**不改订单状态**，订单仍是 `completed`，服务是真实完成的；且**打手的完成榜/收入榜**在部分退款后的口径也各不相同（完成榜把任何已执行退款都排除），说明本仓已接受「部分退款 ≠ 全部否定」。⚠️ 但 (a) 与 (b) 都有道理，**必须由产品定**。
6. **业务差异**：影响「退款能不能消掉评价权」这一整个语义；也与 D20（已评价后退款）互为镜像。**当前行为是「部分退款 = 永久不能评价」，这是一个从未被产品确认过的规则。**
7. **判定**：🔴 **BLOCKING**。

### D19 · 全额退款后能否评价

1. **问题**：订单**全额退款**后还能评价吗？
2. **当前代码事实**：**不能**（同上，`refundStatus === "approved"` 即拦截）。文案「该订单已退款，无法评价」。
3. **原需求事实**：**未定义**（`01-requirements` 零命中）。
4. **选项**：(a) 不能（维持现状）；(b) 能（服务确实发生过，用户有权评价）。
5. **推荐**：(a)。理由：全额退款意味着这笔交易被撤销、打手收益整笔归零（`P0-15`），此时允许打差评会与「收益归零」形成矛盾的双重惩罚。⚠️ 但**这条推荐只是工程直觉**，产品可能有别的立场（例如「全额退款也正是最该被评价的场景」）。
6. **业务差异**：与 D20 共同决定「评价权」与「退款」的先后关系。**当前行为同样是未裁定的代码事实。**
7. **判定**：🔴 **BLOCKING**。

### D20 · 已 `approved` 评价后退款是否撤下

1. **问题**：一条评价**已经审核公开**了，之后这一单发生了退款——评价要不要**自动撤下**（改成 `hidden`）？
2. **当前代码事实**：**没有这个概念**。评价无状态、无撤回路径；退款链路（`lib/services/refunds.ts` / `adminRefunds`）**完全不触碰评价**。当前提交即在列表里可见（对作者），不存在「公开」故也无从「撤下」。
3. **原需求事实**：未定义。
4. **选项**：(a) 不撤下（评价是对当时服务的记录，退款是另一件事）；(b) 自动撤下；(c) 不自动，由管理员决定。
5. **推荐**：(a) 或 (c)。理由：本仓有一条强口径——**「钱」与「行为历史」分开**（`P1-7` 的总规则 `R1`：消费金额随退款实时变化，但累计订单数/游戏频次/服务频次**不因退款而抹掉**）。评价属于「行为历史」一侧，按 `R1` 应保留。⚠️ 但 `R1` 是在**没有审核制**的前提下定的，**审核制引入后是否仍然适用，需产品确认**。
6. **业务差异**：影响退款链路是否要新增一个跨域副作用（退款 → 评价状态），以及平均分是否要随之变化（D14）。
7. **判定**：🔴 **BLOCKING**。

## §一、D1–D22 裁定

### D1 · 一份评价是否同时承载商品 + 打手 —— ✅ RESOLVED

**是。** 一个订单最多存在一个逻辑 `OrderReview`。这一份 Review 是「一次消费的一次评价」，内部可以包含两个评价维度：Product Review · Companion Review。**禁止**为同一订单分别创建第二条「商品评价」和第二条「打手评价」。一单一评的唯一约束继续保留。

### D2 · 商品和打手是否独立评分 / 文本 —— ✅ RESOLVED

**独立。** Review 必须能够分别表达 `productRating` / `productContent` / `companionRating` / `companionContent`。商品评分不能自动复制给打手，打手评分也不能自动复制给商品。

### D3 · 是否必须两个维度都评价 —— ✅ RESOLVED

**不强迫。** 用户可以只评价商品、只评价打手、或两者都评价；**但一次提交至少要包含一个有效评价维度**。
每个被评价维度：**星级必填、文字可选**。
未选择评价的维度：**`rating = null`、`content = null`**。
一次提交成功后，**不允许再回来「补评另一个维度」**——这仍然属于「一张订单最多一次评价」，而不是两次评价机会。
UI 可以鼓励「两项都评」，但**不能强迫**用户为了评价打手而随便给商品打一个无意义的星级。

### D4 · 打手评价对象 —— ✅ RESOLVED

**评价订单最终实际履约打手**，目标取 `final actualCompanion`。**不得**评价 `exclusiveCompanionId`（用户最初指定、但最终没有履约的人）。

### D5 · A → B 换人情况下评价谁 —— ✅ RESOLVED

**本轮只评价最终履约者 B。** 不在一张 Review 内创建多个 Companion Review。A 即使历史上进入过 `serving`，本轮评价系统也**不扩展成多打手评价系统**。
原因：「一次消费一次评价」目前定义为「订单级 Review + 最终履约打手」；历史服务人员的问题主要由**投诉 / 聊天 / replacement history / service history** 承担。未来如真实运营证明需要分别评价多个服务人员，**另起需求，不在 P1-8 发明**。

### D6 · 公开评价显示在哪里 —— ✅ RESOLVED

**商品详情 + 打手详情都公开。**
- 商品详情：商品平均评分 · 商品评价数 · 最近评价
- 打手详情：打手平均评分 · 打手评价数 · 最近评价

**只显示符合公开条件的对应维度。** 例如用户只评价商品 ⇒ 商品侧有贡献，**打手侧完全不产生评分/评价**；反之亦然。

### D7 · 审核状态模型 —— ✅ RESOLVED

四个正式状态：**`pending | approved | rejected | hidden`**。

```
pending → approved
pending → rejected
approved → hidden
hidden → approved
rejected → pending      （只能由用户「重新提交被驳回评价」触发，见 D9）
```

**不得**使用 `Order.status` 或其它领域状态代替 `ReviewStatus`。

### D8 · 作者自己能看到什么 —— ✅ RESOLVED

**作者始终可以看到自己的评价**，包括 `pending` / `approved` / `rejected` / `hidden`，**必须显示清晰状态标签**。
- `rejected`：显示**驳回原因**
- `hidden`：显示「**已被管理员隐藏**」；如果存在 `hideReason`，**也允许作者看到**

审核状态**只控制公开面**，不抹掉作者自己的历史。

### D9 · Rejected 后能否重新提交 —— ✅ RESOLVED

**可以，但不是创建第二条 Review。**
- 同一 `orderId` 仍**只有一个逻辑 Review**
- `rejected` 后作者获得一次「重新提交」入口
- 修改内容后：`rejected → pending`
- **保持同一逻辑 Review identity**
- **不突破一单一评唯一约束**

这是「**驳回后的修正**」，**不是**普通编辑功能。
除 `rejected` 外，用户提交后**不能自行修改**：`pending` 不可改 · `approved` 不可改 · `hidden` 不可改。

### D10 · reject / hide 原因 —— ✅ RESOLVED

**`reject` 与 `hide` 都必须填写原因。** 原因：`trim` 后不能为空、设合理长度限制、**长度沿用项目已有管理员原因字段惯例**（由工程实现统一）。
`approve`：**不要求**原因。
`hidden → approved`：**不要求业务原因，但必须产生 `AdminAudit`**。

### D11 · Hidden 能否重新公开 —— ✅ RESOLVED

**可以。** `hidden → approved`，适用于误操作或复核后恢复。
恢复后：**重新进入公开列表 · 重新计入评分聚合**。

### D12 · 管理员能否修改用户评价内容 —— ✅ RESOLVED

**不能。** 管理员只能 `approve` / `reject` / `hide` / `unhide`。
**不得**改星级、改文字、替用户删除句子、替用户重新措辞。
**原始用户内容只能由用户在 `rejected` 后重新提交。**

### D13 · 公开用户名 —— ✅ RESOLVED

**显示脱敏后的用户昵称。**
**禁止**公开：`userId` / `platformId` / 微信号 / 手机号 / 其它内部标识。
**优先复用项目既有公开昵称 / 脱敏工具**；如果没有稳定公共工具，则建立**一个统一的 formatter**，**不允许商品页和打手页各写一套脱敏规则**。

### D14 · 什么时候计入平均分 —— ✅ RESOLVED

只有 **`status === "approved"`** 的**对应评价维度**才参与 `averageRating` / `reviewCount` / 最近评价列表。
`pending`：**不计**。`rejected`：**不计**。`hidden`：**立即从公开统计中扣除**。`hidden → approved`：**重新计入**。

### D15 · 评分精度 / 空状态 / 最近条数 —— ✅ RESOLVED

沿用当前打手详情的视觉习惯：**平均分 1 位小数** · **没有 `approved` 评价显示「暂无评分」** · **最近评价最多 3 条**。商品侧与打手侧**统一**。
⚠️ 注意：`reviewCount` 必须统计「**该对象实际拥有的 approved 评价维度数量**」，**不能直接统计 `OrderReview` 总条数**。
例如一条 Review 只评商品 ⇒ **product reviewCount +1 · companion reviewCount +0**。

### D16 · 完整评价列表页 —— ✅ RESOLVED

**P1-8 不做。** 本轮：商品详情最近 3 条、打手详情最近 3 条；用户自己的 `/reviews` 继续保留完整「我的评价」。以后如果真实用户需要「查看全部评价」，**再新增公开列表页**。

### D17 · 当前 seed 假评分怎么办 —— ✅ RESOLVED

**彻底退出业务真值。** 当前 `Companion` 的 `rating` / `reviewCount` / `reviews` **不得继续以静态 seed 数字作为真实公开评分来源**，统一改为**真实 `ReviewRepository` 的 approved 聚合**。

**但是**：为了 Mock 演示，可以在 `reviewSeed.ts` 中增加**真实的 `approved OrderReview`** 作为 fixture。
即：**允许「种 Review 数据」，不允许「直接种 `rating=4.8 / reviewCount=3`」**。评分**必须永远由 Review 聚合计算**。**商品侧同理。**

### D18 · 部分退款后能否评价 —— ✅ RESOLVED

**退款比例本身不取消评价资格。** 评价资格仍然看「**这个订单是否满足实际评价条件**」。
部分退款后的 `completed` 订单：**可以评价**。**不得**因为 `refundedAmount > 0` 就永久关闭入口。
退款是**资金结果**，不应自动抹掉用户**真实消费体验**。

### D19 · 全额退款后能否评价 —— ✅ RESOLVED

**不要使用「是否全额退款」作为评价资格判断。** 统一规则：

- **如果订单已经完成服务**（即存在真实 `completedAt`）⇒ 即使之后**部分退款、全额退款**，用户**仍然可以评价**，因为用户确实经历了这次服务。
- **如果订单在完成前就退款**（`paid → refunded` 或 `accepted → refunded`，**从未 completed**）⇒ **不能评价**。

因此：**全额退款 ≠ 自动禁止评价**。真正判断的是「**是否已经完成消费体验**」，本轮以 **`completedAt` 作为明确事实依据**。
**不要为了评价资格重新发明新的「服务完成」状态。**

### D20 · 已 approved 后发生退款 —— ✅ RESOLVED

**不自动撤下评价。** 退款改变的是「**钱**」，不改写「**曾经发生的消费体验**」。
如果评价本身违规，管理员可以**独立执行 `hide`**。**不得**把退款事件偷偷映射成 `approved → hidden`。

### D21 · 不同角色能看到什么 —— ✅ RESOLVED

| 角色 | 可见范围 |
|---|---|
| **用户作者** | 自己的**全部状态**：`pending` / `approved` / `rejected` / `hidden` |
| **游客 / 普通用户** | **只能**看到 `approved` 的公开评价 |
| **打手** | **只能**看到与自己有关且 `approved` 的公开评价。**不得**提前看到 `pending` / `rejected` / `hidden` / 管理审核备注（**避免审核前直接联系用户施压**） |
| **客服** | 允许读取**完整评价信息及状态**，用于售后上下文；但**只能读，不获得审核权限** |
| **Admin** | 完整审核权限 |

**权限必须在服务端控制，不能只靠隐藏按钮。**

### D22 · AdminAudit —— ✅ RESOLVED

所有管理员评价审核动作**必须写入现有 `AdminAudit`**，至少包括 `review.approve` / `review.reject` / `review.hide` / `review.unhide`。
Audit 至少能回答：**谁操作 · 哪条 review · 什么动作 · 什么时间 · 原因（如果该动作要求原因）**。
**不要为评价重新建立第二套审计系统。**

## §二、额外冻结规则 R1–R5

### R1 · 一单一评真正含义

「一单一次评价」定义为：**一张订单只有一个逻辑 `OrderReview`**，内部最多包含一个 Product Review dimension、一个 Companion Review dimension。
**不得**解释为「一单商品评价一次 + 打手评价一次 = 两条独立 Review」。

### R2 · 审核是公开闸，不是数据删除

用户提交后 Review **已经真实存在**。`approve` 只是**允许公开**；`reject` 允许用户**修正后重新提交**；`hide` 只是**停止公开**。
**任何状态变化不得通过删除历史记录完成。**

### R3 · 商品 / 打手聚合必须同源

商品详情和打手详情**不得自己分别计算第二套评分逻辑**。建立**统一 Review 聚合语义（`approved only`）**，然后分别按 `productId` / `companionId` 聚合。**平均分 / 数量 / 最近评价必须同源。**

### R4 · 必须补 `productId`

当前 Review 只有商品标题等快照，**没有 `productId`，无法做真实商品聚合**。P1-8 **必须增加稳定的商品关联**，同时**保留** `productTitle` / `cover` / `specName` 等历史快照。
含义：**`productId` = 聚合身份；快照 = 历史展示事实；二者不能互相替代。**

### R5 · 旧 Review 数据

旧 Review 缺 `productId` / 双维度字段 / `status`。**不得凭空猜测。**
先审查 seed / 当前现存数据能否从**其关联 Order** 可靠迁移：如果能从 `orderId` **唯一、无歧义**地取得 `productId` / `final actual companion` / `rating·content`，**允许做明确迁移策略**。
但旧的一份综合 `rating/content`：**禁止未经产品裁定同时复制成 `productRating` 和 `companionRating`**。
如果存量仅是 **Mock fixture**：**优先重建为符合新模型的真实 fixture**。**不要为了兼容 Mock 假历史污染长期数据模型。**
