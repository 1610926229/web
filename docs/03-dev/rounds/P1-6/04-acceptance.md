## 一、先说清楚：哪些**无法**人工复验，以及为什么

`P1-6` 的规格里有一批要求，**在界面上不存在可复验的入口**——不是没实现，
而是它们约束的是**服务端行为**，界面**故意**不提供触发它们的路径。逐条说明：

| 要求 | 为什么界面上复验不了 | 由什么证明 |
|---|---|---|
| 写操作 Admin only，不得只靠 UI 隐藏 | 登录页只能登进 `admin-1`；被拒身份**进不去后台** | 自动化：匿名 401 → 无权限身份 403（读与写都 403）→ 管理员走到业务校验（`tests/adminCouponTemplates.test.mjs` 的权限矩阵） |
| 非法金额 / 日期必须被**拒绝**而不是被夹取 | 表单在提交前就把非法输入拦住了，到不了服务端 | 自动化：直接调服务层与接口，断言 400 **且零写入** |
| 客户端伪造 `formKey` / `valueLabel` / `id` / 时间无效 | 界面上**没有**这些输入框 | 自动化：往请求体里塞这六个字段，断言全部无效 |
| 停用后已领到的券不可核销 | 需要「先领券 → 再停用 → 再下单」，跨两个端 | 自动化：端到端用例（停用 → 结算页报原因 → 下单 400 → 重新启用 → 同一张券恢复可用） |
| 编辑不追溯历史订单与已领的券 | 需要先造一笔用了券的订单，再回后台改模板 | 自动化：断言订单的券快照 / 实付 / 抵扣额在编辑前后**逐字段相同** |
| 幂等：重复提交不产生第二条记录与第二条审计 | 界面在提交期间禁用按钮，人点不出并发 | 自动化：同键并发 + 重放 |

**验收方式**：这部分请**以自动化测试的通过情况为准**（`pnpm test` / `03-delivery.md` 的终值），
不要因为「界面上点不出来」而判为未实现——那是**故意的**：把「伪造 `formKey`」做成一个能点的按钮，
等于给后台开一个改券形态的入口。

| # | 操作 | 预期 |

### C. 编辑（`/admin/coupons/[id]`）

| # | 操作 | 预期 |
|---|---|---|
| C1 | 打开 `cpn-mock-new-user` 的详情 | 标题「优惠券详情」；先是一块**只读**信息（满减门槛 / 优惠金额 / 形式 / 已领取 / 有效期开始 / 有效期结束 / **建档时间** / **最近更新**），下面是编辑表单 |

### D. 启用 / 停用，以及它会波及谁

| # | 操作 | 预期 |
|---|---|---|
| D1 | 在 `cpn-mock-new-user` 详情页点「停用」 | 状态变「已停用」；再点一次「停用」按钮应当是**禁用**的（已经是那个状态） |
| D2 | 停用后再点「启用」 | 状态变回「已启用」 |
| D3 | **端到端**（需要一个用户账号）：先在用户端领一张券 → 回后台**停用**这张券 → 去用户端的「我的优惠券」 | 券**仍然在券包里**（停用**不删除**任何已发出的券），但在结算页用它抵不了、下单会被拒 |
| D4 | 上一步之后回后台**重新启用**该券 → 再去结算页 | 同一张券**又能用了**（前提是它仍未使用、未过期、满足门槛） |
| D5 | 详情页读一读停用 / 启用按钮旁的说明 | 明确写出两个动作各自会发生什么，以及**本模块不提供删除** |

> ⚠️ **D6｜一条请产品负责人明确的问题（本轮按「满足」处理，但没有蒙混过去）**
>
> 规格 `01-prompt.md` 的「Admin 页面」写的是「至少支持：**列表 / 新建 / 编辑 / 启用 / 停用 / 查看**」。
> 本轮六项能力**都实现了**，但把**启用 / 停用放在了详情页**，列表做成只读（理由见 `02-decisions.md` D2：
> 停用会让已领到券的用户当下不能核销，值得强制「先看清再动手」）。
>
> **规格没有写「启用 / 停用必须出现在列表行内」**，因此本轮判为**满足**。
> 但这句话是否**本来就要求列表上有开关**，`reviewer-agent` 也判定为**它无法替产品决定**。
>
> **请在产品验收时一并回答**：
> - 若「列表行内启停」是**必须**的 → 这是一条**尚未冻结**的要求，本轮**不猜**，请作为验收意见提出，另开一轮；
