## D1｜`/admin/coupons` 归谁：模板列表拿走它，发券搬到 `/admin/coupons/grant`

**背景 —— 一处真实的路径冲突。** P1-4 把**发券**页面放在 `/admin/coupons`
（`app/admin/(console)/coupons/page.tsx`）。而本轮的 §「Admin 页面」明文要求模板管理的三条路径是
`/admin/coupons` · `/admin/coupons/new` · `/admin/coupons/[id]`——**模块首页必须是模板列表**。

**决定：**
1. 模板列表占 `/admin/coupons`（`(list)` 组内，模块首页）；
2. 发券移到 `/admin/coupons/grant`；
3. **底部导航的 href 与文案一个字都不改**（仍然指向 `/admin/coupons`，仍叫「优惠券管理」）——
   导航描述的是**模块**，不是某一张页面；
4. `AdminCouponGrantConsole.tsx` 与 `/api/admin/coupons*` 三个接口**一个字节都不改**：
   它写的是 `CouponClaim`，与模板的增删改是两件事。

**为什么静态段与动态段不会打架：** 同一层里静态段（`grant` / `new`）优先于动态段（`[id]`），
而券 id 的实际取值是 `cpn-mock-*`（种子）与 `cpn_*`（新建），**永远不会**是 `grant` 或 `new`。
构建产物里四条路由并存，已由 `pnpm build` 的输出确认。

**⚠️ 移动方式：普通 `mv`，不是 `git mv`。** 用户本轮明令「禁止任何 Git 写操作」，
而 `git mv` 会把重命名**写进索引**（暂存区），属于 Git 写操作。此前的尝试被权限分类器拦下，
拦得对。

**被否决的做法：** 把发券留在 `/admin/coupons` 而在其下再加一层列表——那会让「模块首页」
指向一个与模块同名的功能子页，并且与规格写死的三条路径直接冲突。

## D2｜列表**只读**，启用 / 停用开关放在**详情页**

**决定：** `AdminCouponTemplateTable` 只显示数据，没有任何会改数据的按钮；每一行的操作列只有
一个「查看 / 编辑」（不可编辑的券是「查看」）链接指向详情页。启用与停用由详情页
（`AdminCouponTemplateConsole`）通过 `enable` / `disable` 两个窄写入接口完成。

**理由一（本仓既有先例）：** `AdminCategoryTable` 的注释已经确立过这条纪律——
「本表只读……表格里放一排会改数据的按钮，等于把「改错了」的概率乘上每一行」。

**理由二（券特有的、比类目更重的一条）：** 券模板停用**直接让已经领到券的用户当下无法核销**
（§5）。在列表上误点一下，后果不是「这一行显示错了」，而是**一批用户手里的券当场失效**。
把写操作放到详情页，等于强制「先看到这张券是什么、已经发出去多少张，再决定动不动它」。

**被否决的做法：** 在列表行上给一个 `enabled` 开关（视觉上最短路径）。除了上面两条，
它还会让「查看」与「改动」在同一个点击目标上争夺注意力。

## D3｜非满减券的两个金额是 `null`，不是 `0`

`discount` / `gift` 模板要能在后台**被看见**（§1「可展示历史模板」），但它们的
`thresholdAmount` / `discountAmount` 在数据里本来就不存在。

**决定：** 这两项以 `null` 出现在 `AdminCouponTemplateItem` 里，页面上显示为 `—`。

**为什么不能用 `0`：** 「满 0 减 0」在数据上是一张**真实存在、且处处可用**的券。
把「没有这个字段」写成 `0`，等于给一张不参与结算的券伪造出一个可结算的外观。

**连带的一条：** `editable`（能不能编辑）由**服务端**用 `isComputableCouponForm(formKey)` 算好后
随 DTO 下发，页面**照着用**，不自己再判一次 `formKey`。两侧各判一次就会出现
「按钮画出来了、点下去 400」——界面与服务端对同一件事给出不同答案。
链接文案（「查看 / 编辑」vs「查看」）与详情页是否渲染表单，都由这一个字段驱动。

## D4｜写入白名单里没有 `formKey` / `valueLabel` / `conditionLabel` / `id` / `createdAt` / `updatedAt`

§1 要求形态只能是 `threshold`，§3 要求文案由金额派生。**决定：** 这六个字段**在请求体里没有位置**——
不是「读了但忽略」，而是 `normalizeCouponTemplatePatch()` 的白名单里根本没有它们。
形态取常量 `ADMIN_COUPON_TEMPLATE_FORM_KEY`，文案由 `buildThresholdCouponLabels()` 当场算，
主键与两个时间戳由伪事务在原子区段里生成。

**理由：** 只要给它们留一个可写的位置，请求体就成了**第二份真值**；而「第二份真值可以被写坏」
这件事不会在界面上显示出来。有一组用例专门往请求体里塞这六个字段（含 `id: "cpn-forged"`），
断言全部无效、且 `cpn-forged` 不存在。

## D5｜有效期输入用**秒**精度，并做一次往返读回

种子里 `cpn-mock-expired` 的 `validTo` 是 `15:59:59.000Z`。

**决定：** `datetime-local` 输入框带 `step="1"`（带秒），并且 `fromDateTimeLocalValue()` 在解析后
**读回一次**核对，拒绝 `2026-02-30` 这类「不存在、但 `Date` 会静默进位到 3 月 2 日」的日期。

**为什么必须带秒：** 若输入框截到分钟，管理员打开这张券、什么都不改、点保存，会让
`validTo` 真的从 `15:59:59` 变成 `15:59:00`——一次「空保存」把用户手里券的有效期改短了 59 秒，
而且**审计上看不出这是误操作**（它确实是一次真实的写入）。

**为什么必须读回：** 静默进位的日期会让管理员以为设了 2 月 30 日，实际生效的是 3 月 2 日。

## D6｜`Coupon` 实体新增 `createdAt` / `updatedAt`，两者都不进任何用户端 DTO

**决定：** 券模板实体带两个时间戳。列表要按建档时间倒序、要显示「最近更新」，没有它们排不了也显示不了。

**边界：** 用户端一个时间戳都拿不到——券面快照、结算页可选券项、订单里的券快照三者的键集合
断言**继续**把它们排除在外（只是**扩**了券模板实体那一条门禁，见 `03-delivery.md`）。

**代价（已同步处理）：** `tests/couponCheckoutChain.test.mjs` 里「券模板 = 券面快照 + id + enabled」
那条精确键集合断言必须同步扩两项。做法是**扩**（把 `createdAt` / `updatedAt` 加进期望数组），
**不是**把它放宽成「包含这两个之外的键」——放宽之后「多一个字段」就再也测不出来了。

## D7｜四个审计动作，重复操作是**空操作**而不是错误

**决定：** 复用既有 `AdminAudit`，动作名为 `coupon.create` / `coupon.update` / `coupon.enable` /
`coupon.disable`，不新建第二套日志（§「Audit」）。

- 「已经就是那个状态」（重复停用一张已停用的券）**不写数据、不写审计、不刷新 `updatedAt`**，
  且**返回成功而不是错误**——它已经是调用方想要的样子。
- 「提交的值与现状一模一样」同样什么都不写。
- 审计快照只收标量，且**不含** `valueLabel` / `conditionLabel` / `createdAt`：
  文案是派生值（§3），把派生值记进审计只会让事后追查的人以为它是另一次改动；
  建档时间不属于「这次改了什么」。

**`updatedAt` 为什么不能白白刷新：** 它是一个会被当作证据的字段。它一变，
事后追查的人就会去找一次并不存在的改动。

## D8｜「重放」与「空保存」在返回值上**不可区分**，这是有意保留的

写结果 DTO 只有四个键：`changed` / `couponId` / `enabled` / `updatedAt`。
因此两者在返回值上都是 `changed: false`。

**决定：** 不为了区分它们而给 DTO 加第五个键。要判断有没有发生第二次写入，
看的是**记录数与审计数**（两条断言即可），而不是返回值。测试就按这个口径写。

**新建的重放靠「操作类型」识别，不靠目标 id：** 新建的目标 id 是在原子区段里**
当场生成**的，第二次调用会生成一个**不同的** id；按 id 比对只会把重放误判成
「这个幂等键被别的对象用了」，从而报一个假的 409 式冲突。`takeCreateReplay()` 因此只认
「这个键已经被同类型的对象用过」，再拿审计里记下的 id 把当时那条记录找回来。

**并发已验证：** 两个同时到达的同键新建请求，第一个写、第二个走重放路径，
最终**一条记录、一条审计、同一个 id**（`tests/adminCouponTemplates.test.mjs`）。

## D9｜发券收窄为「已启用 **且** 参与结算」

§7 明文 disabled 模板不允许发。**决定：** 把这条口径同时用在 `discount` / `gift` 上——
它们虽然可能 `enabled: true`（种子里就有两张），但 §1 明文它们不进 checkout，
发出去也**核销不了**。

**这是收窄既有行为，不是新增能力：** 改的是 P1-4 的 `listCouponGrantOptions()`（可发放列表）
与 `grantCouponToUser()`（发放），两处用同一个判据。发放页的注释也说明了这一点。

**被否决的做法：** 只按 `enabled` 过滤，让管理员选到一张发了也白发（且用户端用不了）的券，
由管理员自己在界面上「看出来」。发放页确实会**警示**不在有效期内的模板（那是「暂时」的，
服务端也不该硬拦），但**形态不对**不是暂时的——它在任何时间点都核销不了。

## D10｜两个上限是**数据完整性**约束，不是产品规则

§2 只写了 `thresholdAmount > 0` / `discountAmount > 0` / `discountAmount <= thresholdAmount`。
本轮另加两个上限：

| 常量 | 值 | 与谁对齐 |
|---|---|---|
| `ADMIN_COUPON_NAME_MAX_LENGTH` | 20（按**字符**，不是字节） | `CATEGORY_NAME_MAX_LENGTH` / `COMPANION_PROFILE_NAME_MAX_LENGTH` 同一量级；手机端券卡片是窄条，名称长了会折行撑变形 |
| `ADMIN_COUPON_AMOUNT_MAX_FEN` | `9_999_999`（99,999.99 元） | 与商品单价的 `SPEC_PRICE_MAX_FEN` **同一个数** |

**为什么这不是在替产品定价：** 上限拦下的是 `99999999999999` 这种手滑。它会造出一张
**永远用不出去**的券，而管理员看到的只是一张「正常保存了」的券——错误发生在保存之后、
很久之后才被发现。

## D11｜券模板的状态色用 `pending`（橙），不用 `danger`（红）

**决定：** `COUPON_TEMPLATE_STATUS_TONE = { enabled: "success", disabled: "pending" }`。

**理由：** 与商品「已下架」同一个理由——它是**可逆的、非终态**的状态。
红色在本仓的既有口径里留给「需要处置」的状态，而一张停用的券不需要任何人去处置。

**⚠️ 这里没有 `muted`（灰）那一档：** §6 不提供硬删除，券模板**不存在终态**。
色板里有档位而语义上没有对应状态，就不该占位。

## D12｜`(list)` 是这一组里**唯一**带 `loading.tsx` 的目录

`app/admin/(console)/coupons/` 下四个路由中，只有 `(list)` 有 `loading.tsx`；
`new` / `[id]` / `grant` 都**没有**。

**理由：** 加载骨架该盖住的是「正在取列表」，不该盖住表单与详情——那两块一旦被骨架替换，
用户看到的是自己刚填的内容消失了一下。已加进 `tests/admin.test.mjs` 的无 `loading.tsx` 断言清单。

## D13｜Mock 空数据范围新增 `"coupons"`，与 `categories` / `products` **分开**

**决定：** `lib/mocks/debug.ts` 的 `MockEmptyScope` 增加一个 `"coupons"`。

**为什么不复用 `categories` / `products`：** 它们清的是别两张列表。
**为什么必须单独一个：** 券模板的券面与**用户端领券中心来自同一份数据**，
因此清空后用户端也会一起空——验收「券模板空态」时要能一眼看出「是空态生效了」，
而不是与别的后台列表混在一起看不出是谁的功劳。

## D14｜明确**没有**做的事（否决清单）

| 否决项 | 理由 |
|---|---|
| 硬删除（`DELETE` / `remove` 路由） | §6 明文不提供；生命周期的终点是「停用」。有一条用例直接**枚举路由目录**，断言不存在第五个地址 |
| 「改券面文案」的入口 | `valueLabel` / `conditionLabel` 是**派生值**（§3）。给它们一个可写位置，文案与金额就会分叉 |
| 复原 `Coupon.enabled` 的两层语义（把快照也一起改） | §4 / §5 明文不追溯。`Coupon.enabled` 只决定「当前能不能核销」，`CouponClaim.snapshot` 决定「这张券是什么」 |
| 建立营销 Ledger / 第二套审计 | 复用既有 `AdminAudit`（§「Audit」明文） |
| 改动结算公式 | 券不改变原价、不降低打手收益、平台承担成本、退款基数是实付——这些由 P1-4 的测试钉住，本轮一行都没碰 |
| 复用排行榜的 `acceptedVia === companion` 判断来判券的返还 | 用户明令禁止；那两条是互不相干的业务线 |
| 信任前端传来的 `discountAmount` / `thresholdAmount` / `couponDiscountAmount` | 前端只传 `couponClaimId`；金额一律服务端算 |
| 触碰 Scheduler / 微信 OAuth / 真支付 / 钱包 / `withdrawn` 追偿 / chat retention | 用户明令「不碰」 |
| 给写结果 DTO 加第五个键来区分「重放 / 空保存」 | 见 D8 |

## D15｜本轮结束时**未提交**

用户本轮指令：「禁止任何 Git 写操作」。因此本轮全部改动（新增文件、修改文件、
路径移动）**保持未提交**，等用户自行 commit。`README.md` 的 `Git Commit` 因此是「无」。

路径移动用的是普通 `mv`（见 D1），工作区状态是「旧路径删除 + 新路径新增」，
**不是** Git 的重命名记录。
