### 1.1 ⚠️ 三条会让验收得出**错误结论**的坑（**先读这一节**）

1. **`收入榜` 在刚启动的应用里一定是空的，六个周期全空。** 这不是没做，而是
   **一份干净的 store 里一条收益都没有**：收益只在订单完成那一刻才产生，
   而它还要**先冻结、后解冻**，收入榜只统计**已解冻**的。详见 §三-C。
   ⇒ **不要看到空就判「收入榜没做」**；正确的判据在 §三-C。
2. **不要先跑 `pnpm test` 再去看榜单。** 全量测试会**真的下单、真的接单、真的完成**
   ——它跑在同一份内存 store 上，跑完之后榜单里的数字**已经被测试污染**，
   而你可能因此认为「数字对不上」。⇒ **要读数字，先重启 dev server，再直接打开榜单。**
3. **「今日」为空是正常的。** 预置数据的时刻锚在**进程启动那一刻**，
   跨天或跨周的边界都可能让某张榜在某个周期上没有数据。

| E2 | 刷新**接单榜** | **A +1、B +0** —— B 是被换进来的，**不算他自己接的单** | 同上 |

## 三、每张榜的最短真实路径

### A. 接单榜（**约 3 分钟**）

1. 用户端切到**老板A** → 下单 → 支付成功（**指定打手**选夜航，或留空走公共池）；
2. 切到**打手身份** → `/companion/orders` → 接单；
3. 打开 `/rank/companions?board=dispatch` → 今日下**多了一次**（若这是今天第一单，则从空变成 1）。

### B. 完成榜（**约 5 分钟**）

接着 A：4. 打手 → 该单 → **开始服务** → **提交完成材料**；
5. 客服 `/staff/login` → `/staff/completions` → **审核通过**（不等 10 分钟自动审核）；
6. 刷新**完成榜** → 该打手今日 **+1**。
   ⚠️ 此时**收入榜仍然是空的**——收益刚产生就处在冻结中（下一步）。

### C. 收入榜（**要么等 ≥60 分钟，要么按 P0-9 的先例用测试代替**）

> ⚠️ **这是本轮唯一一处无法在合理时间内人工观察的验收点**，原因与本轮无关：
> 产品裁定 D17 把**投诉窗口的最小值定在 60 分钟**（默认 **1440**），
> 而收益必须**等这个窗口到期**才会解冻。**P0-9 的人工验收记录里已经有同样的结论
> 与同样的处置**（`P0-9/04-acceptance.md`：已知限制第 5 条「投诉窗口最小 60 分钟，
> 无法在验收中观察到自然到期 → **用测试代替**」）。

**路径一（真实，约 75 分钟）**：管理后台 `/admin/platform-config` 的 **「投诉窗口（分钟）」**
改成 **60**（下界）→ **先改窗口、再走 §三-B 的四步**（⚠️ 这一项**只影响此后完成的订单**，
对已经在途 / 已在审核中的单无效，所以顺序不能反）→ **等到订单完成时刻 + 60 分钟**
→ 打开收入榜。**不需要再点别处**：榜单读路径会自己把已经到期的收益写成 `available`
（本轮补的接线，见 `03-delivery.md` **§6.4**）。

**路径二（P0-9 先例，1 分钟）**：

```bash
node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --import ./tests/alias-hook.mjs \
  --test tests/companionRankings.test.mjs
```

**看这两条**：`端到端：订单完成并解冻后，收入榜按净额记上这位打手`（它断言的就是
「窗口到期后**只读一次榜单**，那笔收益就必须出现，且存储里真的解冻了」）
与 `端到端：有已批准退款的订单不进完成榜（即使它已经 completed）`。

> ⚠️ 提示：`完成材料` 也可以**不审核**——默认 **10 分钟**后自动通过（可配置）。
> 但无论走哪条，**收益都还要再等投诉窗口**，所以收入榜的最短时间由窗口决定。

### 6.1 ⚠️ 全量 HTTP 门禁的**间歇性**失败（如实登记，非本轮引入）

**现象**：生产服务全量复跑共执行 **5 次**，其中 **1 次**失败，失败文件是
`tests/staffRefunds.test.mjs`（该次输出仅剩文件级一行：

```
✖ tests\staffRefunds.test.mjs (744.3588ms)
  'test failed'
```

**其余 4 次全绿**（`1698 / 1698 · fail 0 · skipped 0`，每次都是**全新进程**的服务），
且把 `tests/staffRefunds.test.mjs` **单独**跑一次是 **28 / 28 通过**。

**为什么它不该算在本轮头上**：本轮**没有改动任何退款相关代码或测试**
（`tests/staffRefunds.test.mjs` 不在 §2.1 / §2.2 的清单里），改动面是排行榜域。

**当前最可能的成因（未证实，如实标注）**：`pnpm test` 让**多个测试文件并发**跑在
**同一份 `globalThis` 内存 store** 上，而部分 HTTP 用例**真的会改数据**
（这一点在 §1.1 第 2 条已经作为验收坑写明）。已查到一个**共享写入点**：
`rf-seed-1002-01` 同时是 `tests/adminRefunds.test.mjs`（`LEGACY_PAID_REFUND`）
与 `tests/staffRefunds.test.mjs`（`HTTP_TARGET`）的写入对象。
⚠️ **但单独并发跑这两个文件（70 / 70 通过）复现不出来**，因此**成因尚未坐实**，
不能凭这一条就断定是它——登记为**未定位的间歇失败**。

**对验收的影响**：**不影响本轮的人工验收结论**（人工验收读的是用户端页面，不是这套 HTTP 门禁）。
