## 七、产品负责人裁定（**完整**，2026-09-29 晚段）· 逐字记录

> 本段是**当前唯一有效的产品裁定**。§6.1 的四条**继续有效**（它们是本段的 §1–§4 前半句），
> 本段补齐 §4 后半句并回答其余各项。合起来共 **11 条**。

**§1 本轮范围**
P1 本轮**同时做三张榜**：**接单榜 / 完成榜 / 收入榜**。
P2 的那些项（**综合榜 / 完成率 / 评价 / 投诉率**）**保持 `NOT_IMPLEMENTED`**；
**不得把 P1 的三张榜读成 P2 的综合榜**。

**§2 周期**
三张榜**一律复用现有的六个周期**（`today / yesterday / week / month / lastMonth / all`）
与**现有的 UTC+8 周期实现**；**不得再写第二套周期算法**。

**§3 接单榜的计入口径**
接单榜统计**成功的 `acceptDispatch` 事件**；每一次真实成功接单计 **1**。
例：A → B → A ⇒ **A = 2，B = 1**。
此后的**取消 / 改派 / 完成都不回溯改写历史接单事件**。

**§4 完成榜的计入口径**
完成榜统计**「实际由该 Companion 最终完成的有效订单数」**。计入要求三条同时成立：
1. Order **已完成**；
2. 该 Companion 是**实际完成服务的人**；
3. 该订单**不存在 approved refund**——只要发生过**任何**管理员批准的退款
   （**10% / 50% / 100% 都一样**），该订单都**不计入**。
   原因：退款批准后**打手本单收益归零、打手端本单显示已退款**，
   因此不应继续作为公开「完成业绩」贡献。
   ⚠️ **判断应使用已有的「退款已经实际批准 / 出款」的唯一事实**，
   **不要仅依赖 `Order.status === "refunded"`**，因为**部分退款时真实 `Order.status` 可能仍不是 `refunded`**。

**§5 收入榜的计入口径**
收入榜统计**「已经结算成熟、当前真正归属于打手的净收益」**。本轮口径：
**只统计 `Earning.status === "available"` 对应的 `netAmount` 之和**。
- **不得使用 `Earning.incomeAmount`**——该字段是**历史原始收益快照**，退款后**仍可能保留原值**；
- **不得统计 `frozen`**；
- **不得统计已被退款冲回至 0 的收益**；
- 当前**没有真实 `withdrawn` 写入路径**，因此 P1-5 **不设计 `withdrawn` 口径**。
  未来提现域正式上线后，再单独扩展「`available` + 已提现但真实归属于打手的收益」。
  **当前不要预埋假的 `withdrawn` 逻辑。**

**§6 排序方向与并列规则**
三榜**全部指标越大排名越高**（接单次数 DESC / 完成订单数 DESC / 收入净额 DESC）。
业务名次采用**竞赛排名 / 同值并列**：`100/80/80/50` 显示为 `1/2/2/4`。
同指标值内部，为**接口、分页、渲染稳定**允许用 `companionId` 等**非业务稳定键**排序，
**但该稳定键只决定同分记录的显示先后，不得改变 `rank`**；**不得显示成 `1/2/3/4`**。

**§7 上榜资格**
公开 Companion Ranking 只展示 **`Companion.enabled === true` 且**当前所选榜单当前周期

### 九-A 接单榜的存储底座：**新增只增不改的「接单事件」表**（裁定 §3 / §8 强制要求）

| 事实 | 说明 |
|---|---|
| **问题** | 现模型**算不出** §3 / §8 要求的 A→B→A ⇒ A=2、B=1 |
| 证据 1 | `DispatchRecord` 只有**单个** `acceptedByCompanionId` + `acceptedAt`（`lib/types/dispatch.ts`） |
| 证据 2 | `applyDispatchToPublic()` **显式清空**这两个字段（`lib/data/mockDispatchRepository.ts:120-219`，P0-6 D3 有意为之） |
| 证据 3 | `dispatchIdByOrder` 索引保证**一单只有一行派单记录**——换人复用同一行，早先的接单人**被覆盖** |
| **结论** | 「每次成功接单形成一条历史贡献、永不回写」**必须**有一张只增不改的事件表，否则无从表达 |

**落地**（`lib/types/companionAccept.ts` + `lib/data/companionAcceptRepository.ts`
+ `lib/data/mockCompanionAcceptRepository.ts`）：

- 事件在 `acceptDispatch` 的**无 `await` 原子区段内**追加（与派单/订单/通知同段写完），
  复用 `companionReleaseRepository`（P0-6 履约退出历史）的成熟套路：**仓储接口只读、
  写原语同步导出、只允许伪事务调用**；
- 事件的幂等性**按状态**而非幂等键：`replayed: true` 的重放**不追加**第二条
  （重放分支在写入区段之前就返回了，结构上不可能追加）。

**⚠️ 存量数据的诚实声明**：事件表**建仓时为空**，不伪造历史。
但 `dispatchSeed` 里那些 `state === "accepted"` 的行**本身就是一段真实的接单事实**
（订单的 `acceptedAt` 与它同源），因此读取侧对这**唯一一次**仍可考据的接单做**派生**，
与已记录的事件**去重**，不会重复计数。

> 📌 **实现期收紧（终稿）**：去重键最终取**整个 `dispatchId`**，不是上面原先设想的
> `(派单 id, 打手 id, 时刻)` 三元组。规则一句话：**这条派单已经有记录了吗**——
> 有 ⇒ 它的接单路径已被事件表覆盖，不派生；一条都没有 ⇒ 那是事件表上线前就接好的单，
> 派生它唯一还读得出来的那一次。三元组在正常情况下结果相同，但它多了一个会失败的假设
> （派单记录上的 `acceptedAt` 必须与事件记录**逐字相同**），而计数错了在榜单上是直接可见的错。
> 落点：`mergeAcceptEvents()`（`lib/constants/companionRankings.ts`）。

→ **派生只补「最后一次」**。因此对**历史上发生过 A→B→A 的存量单**，
周期榜数字是**下界**（只数得到最后那次 A）。这是**数据可获得性**的限制，
不是口径的妥协；换成真实数据库后，正确建表即可消除。**本条需产品负责人知悉。**

### 九-B 收入榜的**周期时间基准** = `Earning.frozenAt`（订单完成时刻）

裁定 §5 规定了**数什么**（`available` 的净收益），但**没有规定周期按哪个时间切**。
候选：
- `frozenAt`（= 订单进入 `completed` 的时刻，**非空**、与完成榜同源）；
- `availableAt`（= 计划解冻时刻，**类型上可为 null**，且**实际解冻是惰性物化的**）。

**选择 `frozenAt`**，三条理由：
1. **与完成榜同源**：「本周完成 31 单，其中已成熟收益 ¥2840.50」是同一段业务事实的两种读数，
   不会出现「同一周完成的单，收入算到下一周」这种要额外解释的现象；
2. **不受 sweep 调用时机影响**：`availableAt` 是**计划值**，而真实解冻由「有没有人访问」触发，
   按它切周期会让同一个业务事实在不同机器上落在不同周期；
3. **非空**，不需要为 null 造一条兜底分支（`isWithinRankingPeriod(null) === false`，
   那会把一笔真实收益静默丢掉）。

**影响面**：切换成 `availableAt` 的改动量 = 一处取值 + 两条测试。**本条需产品负责人知悉。**

### ~~九-F 本轮的判断（**已被裁定推翻**，仅存凭证）~~

**这是本轮唯一一处我必须在「写不出代码」和「自己定口径」之间做选择的地方，因此单列。**

**问题**：裁定 §3 说接单榜统计「成功的 `acceptDispatch` **事件**」。但客服的
`replaceOrderCompanionByStaff()`（P0-11 的直接换人）走的是**另一条**写入路径：
它调 `applyDispatchAccepted()` 把派单记录改绑给新打手 B，**不是** `acceptDispatch()`。
裁定**没有对直换表态**——§3 的语境是「打手自己接单」，§4 的「改派不回写历史」
说的是「**不撤销** A 已经发生的那次」。

**不写会发生什么（为什么不能「先不做」）**：读取侧会把**没有被事件覆盖**的
`state === "accepted"` 派单记录**派生**一条出来（`deriveLegacyAcceptEvents()`），
而那条派生通道的**定义域是存量数据**（「事件表上线之前就已经接好的单」）。直换不写事件，
B 就落进那条通道，于是**同一个业务动作出现两种相反的计数**：

| 情形 | 合并结果 | B 的接单数 |
|---|---|---|
| 存量单（从来没有事件） | B 被派生出来 | **1** |
| A 先自己接过（有真实事件）、客服再直换给 B | 合并按 `dispatchId` 整体去重，B 被连带挡掉 | **0** |

**取舍**：本轮选择**写**（`appendCompanionAccept()` 与派单改绑、订单 `accepted`、
通知写在**同一段无 await 的代码**里）。三条理由：

1. **它是写入侧的漏洞，不是口径分歧**。两种计数不可能都对；不写就是让「谁接了」
   这条事实**依赖该单此前有没有被记过**——事实不能取决于它旁边那张表建了多久。
2. **与本仓既有的业务判断一致**：换人对新打手而言**不是「跳过接单」**，他拿到的状态
   与他自己点接单完全一样（`companionOrderTransaction.ts` 的原话，P0-11 起就在）。
3. **不这样选就要动派生通道**，而它**动不了**：要排除「因直换而被接受的」派单记录，
   只能去 join 退出历史里的 `staff_reassign` 记录再比时间，那正是
   `mergeAcceptEvents()` 的注释刚刚论证过**不该引入**的那种脆弱假设。

**⚠️ 这一条是产品裁定之外的判断，请追认**：如果产品的意思是「客服指派**不算**这位打手
自己接的单」，那么正确的改法是**删掉这一条写入**、并**同时**把派生通道收窄
（否则存量与新增仍然不一致）——那是一次两处联动的改动，不是删一行。
追认项已同步登记在 `04-acceptance.md`。

> **📌 事后注（2026-09-29）：产品负责人正是按上面这句「如果」裁定的。**
> 上面估的改动量也被实测证实了——**不是删一行**：除了删掉写入，还要
> 给派单记录加一个「这次绑定是谁发起的」字段（否则派生通道**没有依据**去排除直换，
> 而裁定又不允许它去 join 退出历史比时间），再改派生通道、再补 4 条端到端与 1 条全树门禁。
> 本仓那条「先把它写下来、再请裁定」的路子这回**是对的**：判断被推翻了，
> 但推翻所需的信息（两条路径共用同一个状态迁移函数）与改动量估计**都在纸面上**，
> 所以改正只花了一轮，没有伤到别的实现。
