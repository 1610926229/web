## 二、验收清单

### A. `/admin` 真的不再是入口页

1. 以管理员身份打开 `/admin`。
2. **预期**：
   - 首屏自上而下依次是：**今日经营**（3 张卡）→ **当前待办**（3 张卡）→ **快捷入口**（6 项）
     → **申请与护航规模（全量累计）**（原来那 7 张累计卡，**一张没少**）→ 数据生成时间；
   - 「今日经营」旁边显示 **`业务日 YYYY-MM-DD（北京时间）`**；
   - 累计那一段有**独立小标题**，与上面的「今日」明确区分（防止有人把累计当成今日）。

> ⚠️ **本组要确认的是「旧的东西没被弄丢」**：原来那 7 张卡必须**原样还在**，
> 只是被挪到「全量累计」标题之下。新面板是**叠加**，不是替换。

### B. 今日订单数 / 今日 GMV —— 自造一单，看它涨

1. **先记下** `/admin` 上「今日订单」与「今日 GMV」的当前值。
2. 切到**老板 A**，走一遍下单 → 去结算 → 提交支付；`ENABLE_MOCK_PAYMENT=true` 时
   **支付结果页**会出现「模拟支付成功」按钮（`components/payment/MockPaymentActions.tsx`），
   点它让订单真正形成。**记下这一单的实付金额**。
3. 回到 `/admin`，点一次 **「刷新数据」**。
4. **预期**：
   - **今日订单 = 旧值 + 1**；
   - **今日 GMV = 旧值 + 这一单的实付金额**（不是原价、不是打手收益）；
   - 点 **「今日订单」这张卡** → 进入 `/admin/orders?from=<业务日>&to=<业务日>`，
     **列表条数与卡上的数字一致**（这一步是「卡与明细对得上」的证明）。

### C. ⭐ 关键口径 —— **退款不倒扣 GMV**

> 这是本轮**最容易被做错**的一条，必须单独验。

1. 承 §B，**就用刚才那张今天支付的单**。
2. 以**老板 A** 打开这张单的**订单详情**，用 **「直接退款」** 按钮发起退款
   （`components/refunds/DirectRefundButton.tsx`；`paid` / `accepted` 是**免审批**的，
   **两下才退**：第一下换成说清金额与后果的确认区）。
3. 回到 `/admin`，点 **「刷新数据」**。
4. **预期**：
   - **今日退款 = 旧值 + 这一单的实付金额** ✅
   - **今日订单数 不变**（这一单**今天支付过**，因此仍在今天）✅
   - **今日 GMV 不变**（**退款不倒扣**）——GMV 是「今天成交了多少」，不是「今天净留了多少」✅
5. 卡上的提示文案应当写着「**退款不倒扣**」，与上面的数值行为一致。

### D. ⭐ 关键口径 —— 退款**按发生日**归属

1. 承 §C：那一单是**今天支付、今天退款**的。上面已经算进今天了。
2. **关键点在于**：如果同一笔退款发生在**明天**，它应当算**明天**的，**不**算今天。
   （Mock 环境无法把时钟拨到明天，因此这一条**由自动化测试用固定时间戳覆盖**——
   `tests/adminDashboard.test.mjs` 的「经营 12 / 13 / 14」三条；
   **人工验收这一步只需确认卡片文案说清了这件事**：卡提示上应写着
   「今天实际退出去的金额」、口径说明里应写着「按**退款发生的时刻**归属日期，
   而不是原订单的支付日期」。）
3. ⚠️ **不要**试图用「昨天支付的预置订单今天退款」来人工构造——预置订单未必落在昨天。
   这一格的自动化覆盖是**逐条时间戳断言**，比手工构造更可靠。

### E. 售后**部分退款**也进「今日退款」，且同单多次**按当日累加**

1. 以**打手 夜航**（`u-1022` → `/companion`）从公共池接一单老板 A 的单，并点**「开始服务」**
   （订单进入 `serving`——**只有 `serving` / `completed` 才走售后审核**）。
2. 以**老板 A** 对这张 `serving` 的单**申请售后退款**。
3. 记下 `/admin` 的「今日退款」当前值，去 `/admin/refunds` 走**管理员审批**，
   **按比例**裁定（例如 30%），确认通过。
4. 回到 `/admin`，点 **「刷新数据」**。
5. **预期**：
   - **今日退款 = 旧值 + 这一次实际退出去的钱**（**不是**订单实付全额）✅
   - 若对**同一张单**再走一次部分退款并通过，**今日退款再累加一次**（两次**相加**，
     不是只算最后一次）✅
   - ⚠️ **部分退款不改订单状态**，因此这一单**仍算在今天**，**GMV 也仍然不倒扣**。

### F. 当前待办：三个数字 + 点进去真的到得了

1. 在 `/admin` 上记下 **待处理申请 / 待处理退款 / 待处理投诉** 三个数字。
2. **逐张点进去**：
   - 「待处理申请」→ 应进入**入驻申请列表且已按 `pending` 筛选**；
   - 「待处理退款」→ 应进入 `/admin/refunds?status=pending`；
   - 「待处理投诉」→ 应进入 `/admin/complaints?status=pending`。
3. **预期**：
   - 三个目标页**都真的存在**（不是 404、不是空壳）；
   - 列表里的**条数与卡上的数字一致**（同一筛选口径）；
   - **`0` 照常显示 `0`**，卡片**不消失**——「卡片消失」与「数字为 0」传达的是两件事。
4. **口径核对**（读卡片提示文案即可）：
   - 申请：**待审核 + 审核中**；已通过 / 已驳回 / 用户撤销**不计**；
   - 退款：**待审核 + 审核中**；已通过 / 已驳回 / 已撤销**不计**；
   - 投诉：**待处理 + 处理中**；已处理 / 已关闭**不计**。

### G. 快捷入口：**零假入口**

1. 数一下「快捷入口」有几项（应为 **6** 项），**逐项点开**。
2. **预期**：**每一项都进入一个真实存在的管理模块**，没有 404、没有「即将上线」占位页；
   文案与左侧导航里同一个模块的**叫法一致**。
3. ⚠️ 若发现任何一项指向不存在的页面，**这是缺陷**，请记为 `Issues Found`。

### H. 全 0 是**正常首页**，不是故障

1. 在 `/admin` 的地址后加 `?mockEmpty=dashboard` 打开
   （Mock 调试开关，`ENABLE_MOCK_DEBUG=true` 时可用）。
2. **预期**：
   - 六个数字**全部为零值**且**各自照常显示**：三张经营卡分别是 `0 单` / `¥ 0.00` / `¥ 0.00`，
     三张待办卡都是 `0 条`（**不是空白、不是 `NaN`、不是 `--`**）；
   - 「今日经营」下面出现一句说明：**「今天还没有成交记录」**，并解释「本地 Mock 数据重启会回到预置数据、预置订单也未必落在今天」；
   - 「当前待办」下面出现一句：**「当前没有需要管理员处理的申请、退款或投诉。」**；
   - ⚠️ **整页不得出现 EmptyState 之类的空页面**——`今日订单 = 0` 是一个**正常的 Dashboard**。
   - 原来那 7 张**累计卡仍在**（它们不受 `mockEmpty=dashboard` 影响）。

### I. 四个状态：loading / error / retry

> ⚠️ **这里有两种**错误态，**不要混淆**——它们的触发方式不同：
> **① 整页错误**（服务端渲染就失败，交给 `app/admin/(console)/error.tsx`）；
> **② 局部错误**（首屏正常，只有「刷新数据 / 重试」这一次请求失败，在经营区域内显示）。
> `?mockError=…` 这个调试参数**只作用于 URL 上的那一次服务端取数**，
> **不会**跟着「刷新数据」按钮发出的请求走（那个请求打的是 `/api/admin/dashboard`，不带参数）。

1. **loading**：在 `/admin` 后加 `?mockDelay=1500` 打开，
   **预期**：先看到与真实布局**同形**的骨架（今日经营 3 张 + 待办 3 张 + 快捷入口 6 项 + 累计 4 列），
   加载完成后**不出现明显跳动**。
2. **① 整页错误 + 重试**：在 `/admin` 后加 `?mockError=1` 打开，
   **预期**：整页进入错误态（`admin/(console)/error.tsx`），有错误说明与**重试**按钮；
   点重试会重新渲染一次。⚠️ 只要地址上还挂着 `?mockError=1`，**它会再失败一次**
   ——这是注入的**预期行为**，不是重试没生效；去掉该参数再点即可成功。
3. **② 局部错误 + 重试**（**这是「刷新数据」那条路**）：
   - 正常打开 `/admin`（不带任何调试参数），首屏六个数字应**正常显示**；
   - 打开浏览器**开发者工具 → 网络**，把 `/api/admin/dashboard` 这个请求**阻断**
     （或用「离线 / Offline」模式）；
   - 点 **「刷新数据」**；
   - **预期**：今日经营区域出现一条红色提示（`role="alert"`）与一个 **「重试」** 按钮，
     **标题、业务日与两条口径说明仍然在位**——是**局部**失败，不是整页崩掉；
   - 解除阻断后再点 **「重试」** → 数字恢复。
4. 另**单独**验一次正常路径的 **「刷新数据」**：数字应重新取一次（**不整页重载**、
   **不闪烁**、地址栏不变）。

### J. 权限：不是管理员就进不去

1. **匿名**（无痕窗口）直接开 `/admin` **和** `GET /api/admin/dashboard`
   → **预期**：进不去（接口 **401**）。
2. 以**普通用户**（老板 A，只有用户 Cookie）打开 `/api/admin/dashboard`

3. 以**打手**（`u-1022`）打开同一接口 → **预期**：**401**。

### K. 首页**只读**：上面一个会改数据的按钮都没有

1. 在 `/admin` 上通读一遍：所有可点的东西都是**链接**（跳到别的模块处理业务）。
2. **预期**：首页上**没有**审批通过 / 驳回、没有退款、没有换人 / 回池、没有封禁、

3. ⚠️ 「刷新数据」与「重试」只是**重新读一遍**，不写任何东西。

## 三、通过标准（PASS / FAIL）

**PASS 的条件（全部满足）**：

- §A 今日经营 / 当前待办 / 快捷入口三段出现，且**原来那 7 张累计卡一张没少**；
- §B 「今日订单 / 今日 GMV」在自造一单后**按预期增长**，且**卡与明细列表条数对得上**；
- §C **退款不倒扣 GMV**（**本轮最核心的一条**）；
- §E **售后部分退款进今日退款**，同单多次**按当日累加**；
- §F 三类待办**点进去到得了**且**条数一致**，`0` 显示 `0`、卡片不消失；
- §G 六个快捷入口**零假入口**；
- §H 全 0 是正常首页，**不整页空态**；
- §I **loading / error / retry / 正常**四态齐全；
- §J 匿名 / 用户 / 打手 / 客服**四条拒绝**、管理员**一条放行**（正反例都验）；
- §K 首页**只读**。

**FAIL 的判定**：上述任一条不满足，或出现下列任一种情况——

- 「今日 GMV」在退款后**变小**了（说明倒扣了）；
- 「今日退款」把**昨天的退款**算进了今天（归属日判据用错）；
- 「今日退款」把**同一笔**退款算了两次（重复计数）；
- 用 `Order.refundedAmount` 之类**累计值**去算「今日」（表现为跨日退款时数字偏大）；
- 待办卡点进去 **404**，或卡上的数字与列表**明显对不上**；
- 首页上出现了**任何会改数据的按钮**；
- 非管理员**能拿到** `/api/admin/dashboard` 的数据。
