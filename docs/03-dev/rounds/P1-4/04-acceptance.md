## 五、如实登记的缺口与已知边界（**验收时请一并知悉**）

这一节列的**不是**「没做完」，是「**明确不覆盖**或**依赖别处**」，写清楚以免被误读成已覆盖。

1. **「后台改券不追溯历史订单」（cmd 第 6 条）只能靠自动化验证，没有界面可以做。**
   本项目**没有**券模板的后台管理入口（`app/api/admin/` 下没有任何 coupon 路由），
   所以「改券」这件事在界面上做不出来：用例是**直接改 mock 存储里的模板**再断言历史订单不变。
   ⚠️ 裁定 §9 要求的行为已实现并被钉住，但**等后台真的有了改券入口时，应该补一条端到端验收**。
2. **「门槛正好等于」这一格手工很难凑出来**：需要金额**恰好** ¥100.00，而商品价、增值服务价与数量的组合并不能保证凑得出正好这个数。该边界由自动化断言钉死（正好等于通过 / 差 1 分拒绝 + 两个入口同一句原因）。手工验收请只验「未达门槛被拒 + 原因带上两个金额」（A4 / A5）。
3. **`buildOrderFromRequest` 里「核销成功 → 建单」之间的残余窗口未消除，只收窄到无 `await`**。
   订单与券核销记录在两个 Mock 存储上，没有跨存储事务，**架构上关不严**。当前 mock 实现里这段没有已知抛错点，但这不是不变量。代码内已如实注释（本轮按 reviewer 意见把注释改成**不夸大也不缩小**）。
   ⚠️ **换成真仓储时必须重新处理这一段。**
4. **React 组件行为（结算页三行渲染、选中券后的即时重算）没有自动化覆盖**：`node --test` 不剥离 JSX，组件行为在测试框架之外。**这是本轮唯一的验证方式缺口**，只能人工验（§二-A）。
5. **打手端订单详情「订单合计」仍显示优惠前金额**：`app/companion/(console)/orders/[id]/page.tsx:279` 读的是优惠前 `totalAmount`。
   这个值同时**是打手的收入基数**，改动属于产品 / UX 判断，**不在任何已裁定规则的覆盖范围内**——因此**保留原样并在此点出**，没有自行决定。**若产品认为打手也该看到实付口径，请下发规则，我再改。**
6. **消费额的口径只解决「有券时读哪个字段」**：`database-schema.md` 里那条**部分退款是否按实退扣减消费额**的 TBD（`Σ max(0, actualPaidAmount − refundedAmount)`）**本轮刻意未碰**，仍未裁定。§二-F 验的是有券订单，不涉及部分退款扣减。
7. **页面尺寸**：结算页是**移动端 H5**（微信内打开），管理端 / 客服端页面是 **PC 后台**，沿用各自既有设计体系。

| **A** | **停用的券不能再被使用**：结算时读**券模板当前**的 `enabled`。用户领取时券是启用的，之后平台把它停用了 → **不能用** | 领取时已启用的券，即使后来停用也**仍可使用**（即以**领取快照**的启用状态为准） | 一个 `if` 分支 + 对应测试 |
| **B** | **以领取快照为准定价**：领取后后台改了券面额/门槛，**已领的券按领取时**的值抵扣（D-P1-4-2） | 以券模板**当前**值为准（已领的券也跟着变） | 取值来源换一处 + 对应测试 |

> 我选 A 的理由：停用是平台主动收回一个权益，让它对已领用户继续生效，等于停用按钮按下去还有一段尾巴。
> 我选 B 的理由：券一旦被领走就是一份「已经发出去的承诺」，后台改模板不应追溯改动它——这与裁定 §9「后台改券不得改变历史订单金额」是同一个方向。
>
> ⚠️ **请注意**：A 与 B 在方向上**正好相反**（A 认「当前」，B 认「快照」）。这不是疏漏，而是两种判断的对象不同：**能不能用**是平台的**风控/运营**动作，**抵多少钱**是已经发放的**承诺**。若您认为两者应该统一到同一个方向，请明示。

兑现方式：请在下面勾选或直接改写。

```
[x] A 维持现状（停用即不可用）              ← 2026-09-29 产品负责人勾选
[ ] A 改为「以领取时的启用状态为准」
[x] B 维持现状（以领取快照定价）            ← 2026-09-29 产品负责人勾选
[ ] B 改为「以券模板当前值定价」
```

> ⚠️ 表里那句「若您认为两者应该统一到同一个方向，请明示」**已经有了答复，而且是不统一**：
> 「能不能用」问当下（平台现在许不许用），「抵多少钱」问当初（当初答应了什么）。
> 这两句问的本来就不是同一件事，所以它们的时间语义不同**不是**矛盾——
> 把两者强行统一，必然在另一头出错。**本批不再就这一点提出任何追问。**

### 7.1 本轮修的是什么（验收时请重点盯这一条）

第一轮验收现场看到的缺陷：**「我的优惠券」里显示可用的券，结算页却说「暂无可用优惠券」**。
根因是同一个判断被写了两遍。本轮把它收敛成一个前置判定，两处共用。

| # | 操作 | 预期 |
|---|---|---|
| 🔴 **R1** | 用 `u-1001` 登录，进「我的优惠券」，**逐张记下每张券下写的可用性** | 「新人立减券」= **可用于结算**；「无门槛体验券」（立减 5）= **暂不可用于结算（当前仅满减券参与结算）**；「节日折扣券」= **该券已使用**；「暑期活动券」= **该券已过有效期，无法使用** |
| 🔴 **R2** | 用同一账号进结算页（`p-400w` / `s-400w`，数量 **4**，合计 ¥119.60），展开优惠券 | 「新人立减券」**必须出现在可选列表里**，选中后**三行**：原价 ¥119.60 · 优惠券 −¥10.00 · 实付 **¥109.60**。⚠️ **这就是人工验收那个缺陷的回归**——账户里写「可用于结算」的券，结算页必须给得出来 |
| 🔴 **R3** | 同一单把数量改成 **1**（合计 ¥29.90） | 那张券**仍在列表里、但不可选**，并写明差额：**「满 ¥100.00 可用，还差 ¥70.10」** |
| R4 | 把数量调回 4 再调回 1，反复几次 | 可用性**当场跟着变**，不会停在某个旧结论上 |

> **R2 的判据不是「页面长得对」，是「两处对同一张券的看法一致」**：
> 账户页说能用于结算的券，结算页必须给得出来；账户页说不能的，结算页也不能偷偷给。
> 这几个判断今天由**同一个函数**产生，所以它们**不可能**再分叉。

### 7.2 🔴 退款**会返还优惠券**（本轮的**行为反转**，请重点确认）

⚠️ **这一条与第一轮相反。** 第一轮的规则是「退款不退券」；本轮产品裁定 §一 改为
**「订单**曾经**进入过 `accepted` 就不还券；从未被承接的单，退款要把券还回去」**——
判据是「有没有被承接」，**不是**退款比例，也**不是**退款那一刻的状态。

| # | 操作 | 预期 |
|---|---|---|
| 🔴 **R5** | 用「新人立减券」下一单（¥119.60 → 实付 ¥109.60）并**支付成功** | 券变**「已使用」**；订单详情里的券快照指向它；**这一单不要让人接单** |
| 🔴 **R6** | 在这张订单详情页点**「全额退款」**（`paid` 单走的是**免审批直接退款**，不是管理员审批） | 退款成功；**券回到「未使用」**，且**账户页立刻显示「可用于结算」** |
| 🔴 **R7** | 拿这张刚退回的券**再下一单**并用掉 | **可以正常使用** —— 归还的是**未使用资格**，不是一张被作废的券 |
| 🔴 **R8** | 另起一张券订单，支付成功后**让打手接单**，**再**退款 | 券**不返还**（仍是「已使用」）—— 这一单**被承接过了** |
| 🔴 **R9** | 接着验「曾经」二字：让打手接单后**主动取消**（订单退回 `paid`），**再**退款 | 券**仍然不返还** —— 订单**曾经**进入过 `accepted`，即使现在看起来又回到 `paid` |

> R9 是裁定 §一「**曾经**」二字的边界，也是最容易被误判成 bug 的一格：
> 订单退回 `paid` 会清掉 `acceptedAt`，但**不会**清掉「曾被承接」这个历史事实。
> 因此判据刻意**不**看退款瞬间的 `status`——那样 R9 会错误地还券。

### 7.3 🔴 管理员向指定用户发券（本轮新增能力）

管理端侧栏新增 **「优惠券发放」**（`/admin/coupons`）。

| # | 操作 | 预期 |
|---|---|---|
| 🔴 **R10** | 进 `/admin/coupons`，看模板列表 | **只有当前启用**的券模板；**已停用的模板不出现**（发出去一张用不了的券没有意义） |
| 🔴 **R11** | 搜一个用户（关键词可打 `u-1002` / 昵称 / 展示号），注意列表上的数字 | 显示这个人**已经持有几张**券（**不分模板**）。发放**允许重复**，所以这个数字是给管理员看的，不是拦截 |
| 🔴 **R12** | 选「新人立减券」发给一个**从来没有领过券**的用户 | 发放成功；该用户「我的优惠券」里**立刻多一张**，来源标为**管理员发放** |
| 🔴 **R13** | 对**同一个用户、同一个模板**再发一次 | **允许**（与用户自己领的「一模板只能领一次」**不是**同一条规则）；用户手上变**两张**，各自独立可用 |
| 🔴 **R14** | 发的时候注意有效期提示 | 若模板**已过期**，界面给出**警告**（⚠️ 不在有效期内，发出的券将无法使用）——**警告是提示，不是拦截** |
| R15 | 未登录直接访问 `/admin/coupons` 或直接请求发券接口 | **401**（管理端鉴权自己的会话；用户端 Cookie 换不来管理权限） |

### 7.5 本轮如实登记的缺口（**验收时请一并知悉**）

1. **`CouponClaim.source` 的「必填」在 `.mjs` 测试夹具里不生效**：生产代码六个构造点全部由
   编译期强制，**唯一**漏洞是测试自己构造 Claim 时可能漏写。不影响线上行为。
2. **`app/admin/(console)/` 下没有 `loading.tsx`**（**既存问题，非本轮引入**）：该目录的

3. **发券界面的交互（两个选择列、搜索、幂等重放）只能人工验**：`node --test` 不剥离 JSX，

4. **曾经担心过的「部分退款也会还券」，查证后不成立**，因此**没有**这条缺陷：
   `paid` / `accepted` 走的**直退**路径**没有比例参数**（恒定全额），而带比例的**审批**
   路径只对 `serving` / `completed` 开放——这两档**必然**已被承接，**根本不会还券**。
