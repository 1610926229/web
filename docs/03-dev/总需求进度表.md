# 总需求进度表

> 文件定位：本文件是项目全局需求进度的唯一总览，用于 Claude / Agent / 人工快速判断当前项目做到哪里、下一步做什么、依赖什么。
>
> 编码：UTF-8
>
> 维护原则：
> - 本文件只记录全局进度，不承载每个 Round 的完整提示词、问答、实现报告和验收记录。
> - 正式 Round 的详细历史应记录在 `docs/03-dev/rounds/<ROUND_ID>/`。
> - Claude 完成编码不等于 DONE；只有人工验收通过并由用户自行完成 Git commit 后，才能将对应 Round 标记为 DONE。
> - 若长期需求文档、Round 决策与本表出现冲突，应进入 CLARIFYING，不得静默覆盖。
> - **2026-09-23 需求重校准规则**：历史 Round 按当时已确认需求保留真实完成状态；后续产品规则变化通过新的 `NEEDS_FIX / PLANNED` 条目承接，禁止把已完成历史改写成“从未完成”。

## 状态说明

| 状态 | 含义 |
|---|---|
| ✅ DONE | 已完成并验收，可作为后续开发基础 |
| 🟡 PARTIAL | 已有基础能力，但业务闭环不完整 |
| 🔵 IN_PROGRESS | 当前正在开发 |
| 🟣 AWAITING_ACCEPTANCE | 编码与自动门禁已完成，等待用户人工验收。**未经用户验收通过不得视为完成**（`DONE` 另需用户本人提交）。⚠️ 人工验收**已通过**、但**用户本人尚未提交**的轮次，状态**仍然停留在此**，`Next Step` 列会写明「等待用户本人 Git 提交」 |
| ⏳ PLANNED | 已明确需要开发，但尚未开始 |
| 🟠 NEEDS_FIX | 已有实现，但口径或联动仍需整改 |
| ⏸ PAUSED | 当前明确暂停或暂缓 |
| 🔴 PRODUCTION_BLOCKER | Mock 阶段可以继续，但生产上线前必须解决 |

**机器读取必须使用英文状态码**（`DONE` / `PARTIAL` / `IN_PROGRESS` / `PLANNED` /
`NEEDS_FIX` / `PAUSED` / `PRODUCTION_BLOCKER`）。**emoji 仅供人类阅读。**

## 列说明

| 列 | 含义 |
|---|---|
| `Round` | 正式开发批次 ID。`UNASSIGNED` 表示**权威文档尚未给出正式编号**——不代表该需求不存在或被取消。**编号由用户 / ChatGPT 在正式启动该轮时分配，Claude 不得自行创造。** |
| `功能 / 目标` | 该行的业务名称与要解决的问题 |
| `Status` | 上述标准英文状态码 |
| `Depends On` | **只记录原表已写明的依赖**，不自行推导。无依赖写 `—` |
| `Blocker` | **只记录真正阻止当前阶段继续的事项。** 生产上线阻塞项记在 `Status`，普通依赖不算 blocker |
| `Round Record` | 该轮的历史档案状态，取值见下表 |
| `Next Step` | 仅根据原表已有信息填写；无则 `—` |
| `Notes` | 原表的「当前实现情况」与「为什么现在这样 / 依赖什么」，**不删减** |

### Round Record 取值

| 取值 | 含义 |
|---|---|
| `LEGACY — before Round Protocol` | 协议建立前完成的基础能力，**不补档案** |
| `LEGACY — completed before Round Protocol` | 协议建立前已完成并验收的正式批次，**不补档案** |
| `PRE-PROTOCOL — development already in progress` | 协议建立时已在开发中途，**不倒填历史** |
| `—` | 尚未开始；Round 档案待该轮正式启动时创建 |

**⚠️ 从下一轮起**，每轮必须完整包含 `docs/03-dev/rounds/<ROUND_ID>/` 的五个文件
（见 `development-workflow.md`）。**不存在的历史不伪造。**

## 维护规则

1. 本表只记录全局进度，不记录完整开发过程。
2. 新 Round 开始后，只更新对应阶段的 Status、Blocker 和下一步。
3. 某功能完成编码后，状态最多进入“等待人工验收”，不直接标记 DONE。
4. 用户人工验收通过且自行 Git commit 后，才允许更新为 `✅ DONE`。
5. 如某项需求出现未确认产品规则，应保持非 DONE 状态，并进入对应 Round 的 `02-decisions.md`。
6. 不因为代码“已经存在”就认定业务已完成；必须以真实业务闭环和验收结果为准。
7. **`Round` 列不得由 Claude 自行创造编号**——未来需求的编号由用户 / ChatGPT 在正式启动该轮时分配。
8. **禁止无授权 Roadmap 重排。** Claude / Agent 不得自行合并、拆分、改优先级或创造 P0/P1/P2；但当产品负责人明确修改需求或优先级时，应更新本表，并保留旧 Round 的历史真实状态。
9. **历史 DONE 不倒退。** 后续规则变化导致旧实现不再满足当前产品目标时，新增 `NEEDS_FIX / PLANNED` 条目承接，不把当时已经验收并提交的历史 Round 改成“从未完成”。
10. **CURRENT 与 TARGET 分开。** 已实现事实写 CURRENT/当前实现；新确认但尚未编码的行为写为 `PLANNED / NEEDS_FIX`，不得把需求文档的目标行为冒充成源码现状。
