# 超哥电竞｜用户权限表

版本：V0.1  
基线日期：2026-09-19  
用途：作为页面权限、API 权限、DTO 数据最小化、角色边界、测试门禁的开发基线。

> 本文件只回答“谁能看什么、谁能做什么”。业务状态转换以《业务流程表》为准。

# 1. 角色定义

| 角色 | 定义 |
|---|---|
| 游客 | 未登录访问者 |
| User / 用户 / 老板 | 平台基础用户，可购买服务 |
| Companion / 打手 / 护航 | User 具备有效 Companion 资格后的附加能力 |
| Customer Service / 客服 | 平台工作人员，处理会话、审核、投诉、售后等 |
| Admin / 管理员 | 平台经营、配置、资金、权限的最终管理角色 |
| System / 系统 | 自动超时、自动退款、通知、未来结算等非人工执行者 |

# 2. 身份与账号原则

## 2.1 User 与 Companion

Companion 不是独立登录账号。

```text
User Session
→ userId
→ Companion qualification
→ Companion capability
```

同一个人可以同时：
- 作为用户下单；
- 作为打手接其他用户订单。

不得新增：
- Companion 独立 Cookie；
- Companion 独立登录页；
- Companion 第二套 Session。

## 2.2 enabled 与 available

| 字段 | 含义 |
|---|---|
| `enabled` | 是否仍具有有效打手资格 |
| `available` | 是否当前允许接受新订单 |

两者不能混为同一个权限。

### PR-01 `available=false` 的可见性与接单权限 ✅

2026-09-20 正式确认（原「当前建议」原样采纳）：

- 可以进入打手工作台（`available` 不参与资格判定）；
- 公共池不返回可接订单，因此不能接受新公共池订单；
- 已经属于自己的专属派单可以看到，但不能成功 accept；
- 恢复 `available=true` 且 deadline 未过，可继续接。

关联：EX-AUTH-04、BR-01、Q-EX-01。

# 4. 游客权限

允许：
- 浏览首页；
- 浏览商品；
- 搜索；
- 浏览分类；
- 查看商品详情；
- 浏览陪玩列表；
- 浏览排行榜；
- 查看帮助/活动等公开入口。

禁止：
- 创建交易；
- 支付；
- 查看个人订单；
- 进入私有用户数据；
- 申请退款；
- 进入打手工作台；
- 进行任何管理操作。

# 5. User / 老板权限

## 5.1 商品与交易

允许：
- 浏览所有公开商品；
- 创建 Checkout；
- 创建 PaymentRequest；
- 支付自己的订单；
- 选择指定打手或不指定；
- 查看自己的订单；
- 查看自己的订单金额和履约状态。

禁止：
- 查看他人的订单；
- 读取平台内部成本；
- 读取管理员备注；
- 指定最终实际接单人；
- 直接修改订单状态。

## 5.2 指定打手

User 可以表达：

```text
“我希望 A 服务”
```

即：

```text
Dispatch.exclusiveCompanionId = A
```

User 无权直接指定：

```text
Order.actualCompanionId
```

实际履约人只有成功接单以后才能确定。

## 5.3 投诉与退款

User 只能对自己的订单发起投诉/退款。

退款可申请状态：

### 待确认 PR-02

尚未正式确定。

# 6. Companion / 打手权限

## 6.1 身份来源

必须先拥有有效 Companion 资格。

不是独立账号。

## 6.2 工作台访问

`enabled=true`：

可以进入工作台。

`enabled=false`：

不允许继续进入正常打手业务域。

removed：

运行时表现为当前 User 已不再具有 Companion 资格。

## 6.3 订单池

### 专属池

只能看到指定给自己的专属派单。

其他打手不得看到。

⚠️ 例外：这一单是**他本人下单**的时候，即使 `exclusiveCompanionId` 就是他，也不返回（EX-DISPATCH-08）。

### 公共池

只能看到业务规则允许当前 Companion 接取的公共订单。

⚠️ 因此**本人下单的订单不在其中**：池子 DTO 不含 `userId`，他本来也分不出哪张是自己的，返回它等于在页面上承诺一件点下去必然失败的事（EX-DISPATCH-08）。

### PR-01

`available=false` 时最终规则已确认，见 §2.2 `PR-01` 小节。

## 6.4 接单

接单 API 必须使用：

```text
requireCompanion()
→ 当前 companionId
```

不得从请求体接受 companionId。

接单成功后：
- 成为 actualCompanion；
- 不能主动放弃；
- 不能自己退回公共池。

## 6.5 接单前数据权限

接单前不得查看：
- 游戏账号；
- 敏感用户备注；
- 用户其他订单；
- 管理员备注；
- 内部财务；
- 其他用户数据。

## 6.6 接单后数据权限

actualCompanion 可以查看当前订单履约必要数据：
- 订单号；
- 商品；
- 规格；
- 游戏；
- 区服；
- 必要用户信息；
- 游戏账号；
- 服务要求；
- 用户备注；
- 增值服务。

不得查看：
- 用户其他订单；
- 平台内部财务；
- 管理员内部备注；
- 其他用户数据。

## 6.7 开始服务

未来权限：

只有：

```text
actualCompanionId == 当前 companionId
```

且：

```text
Order.status == accepted
```

才能执行：

```text
accepted → serving
```

## 6.8 完成材料

未来权限：

只有：
- 当前 actualCompanion；
- Order.status == serving；

才能提交 CompletionSubmission。

打手不能直接把订单改为 completed。

## 6.9 打手收益

未来只能查看自己的 Earning / 余额 / 提现记录。

不能查看：
- 其他打手收益；
- 平台总体利润；
- 用户其他支付信息。

# 7. 客服权限

客服定位：

```text
调查 + 沟通 + 完成审核 + 售后处理 + 退款建议
```

不是最终资金审批人。

## 7.1 可以

客服可以：
- 使用客服工作台；
- 查看工作所需订单；
- 查看订单相关会话；
- 审核打手完成材料；
- 通过/驳回 CompletionSubmission；
- 处理投诉；
- 调查售后；
- 提交退款建议；
- 与用户沟通；
- 与当前实际打手沟通；
- 查看历史 assignment 聊天用于调查。

## 7.2 不可以

客服不能：
- 修改商品；
- 修改分账比例；
- 修改平台公共池 timeout；
- 最终批准退款资金；
- 随意修改打手收益；
- 以 Companion 身份接单；
- 代替正常打手执行普通开始服务；
- 绕过状态机随意把订单设为 completed。

## 7.3 退款边界

客服可以调查和提出建议。

最终退款比例由管理员决定。

## 7.4 多客服分配

### 待确认 PR-03

多个客服未来采用：
- 所有客服看全部待处理项；
- 或每个会话/投诉/退款分配具体负责人；

尚未确认。

# 8. 管理员权限

管理员定位：

```text
平台规则 + 经营配置 + 人员权限 + 最终资金权 + 监督
```

## 8.1 商品与内容

管理员可以：
- 创建/编辑/下架商品；
- 管理规格；
- 管理商品类目；
- 设置商品分账比例；
- 修改公告；
- 修改协议；
- 修改首页展示内容；
- 管理其他运营内容。

## 8.2 Companion 管理

管理员可以：
- 审核入驻申请；
- 启用；
- 停用；
- 移除；
- 设置 available；
- 未来设置 B/A/S；
- 未来配置并发上限。

### 待确认 PR-04

停用/封禁已有订单时：
- accepted 未 serving 怎么办；
- serving 怎么办；

尚未正式确认。

## 8.3 订单

管理员可以：
- 查看全平台订单；
- 查看“指定护航”和“实际接单”；
- 查看必要派单历史；
- 查看资金快照；
- 查看售后和投诉关联信息。

管理员不应通过普通 UI 随意直接改 OrderStatus。

特殊人工干预必须：
- 有明确业务场景；
- 有审计记录；
- 不破坏资金和派单历史。

## 8.4 退款/资金

管理员拥有：
- 最终退款比例决定权；
- 平台资金相关最终管理权限；
- 未来提现审核等最终资金权。

不能绕过系统公式手工随意改最终资金数据。

## 8.5 平台配置

管理员可以修改：
- 公共池超时时长；
- 商品分账比例；
- 未来 B/A/S 并发上限；
- 其他明确开放的平台参数。

历史订单已冻结快照不随未来配置变化。

## 8.6 客服管理

管理员可以：
- 添加/管理客服账号；
- 控制客服权限范围；
- 查看客服业务处理结果；
- 查看相关审计。

# 9. System 权限

System 不是人工角色，只允许执行已经定义好的自动规则。

| 动作 | 规则 |
|---|---|
| 专属池超时转公共池 | deadline 到达且无人接 |
| 公共池超时停止接单 | deadline 到达 |
| 公共池自动全额退款 | public timeout |
| 发送生命周期通知 | 业务事件成功后 |
| 48h 投诉窗口到期 | future |
| frozen → available | future |
| 普通聊天到期删除 | future |

System 不能：
- 发明退款比例；
- 改商品价格；
- 指定某个人接单；
- 绕过条件强制 completed；
- 执行没有产品规则的罚款。

# 10. 数据最小化要求

任何 API / DTO 都按“当前角色完成当前任务所需的最小字段”返回。

## 公共池 DTO

不应包含：
- gameAccountId；
- remark；
- userId；
- 管理员备注；
- 平台财务。

## actualCompanion 订单详情

可以增加当前履约必要字段。

## User 订单详情

只能看到自己的订单。

## 客服

只开放履职需要的信息。

## 管理员

可以看到全局管理所需数据，但敏感操作仍需权限与审计。

# 11. 管理审计要求

以下人工管理动作原则上应审计：
- 修改平台参数；
- 修改商品；
- 修改商品分账比例；
- 审核打手；
- 启用/停用/移除打手；
- 客服账号管理；
- 最终退款批准；
- 未来提现审批；
- 其他资金或权限变更。

自动生命周期动作通常属于领域事件，不等同于 Admin Audit。

例如：
- 公共池 timeout；
- 自动退款；
- 普通聊天到期删除；

由系统事件记录业务事实，不伪装成管理员动作。

# 13. 权限开发纪律

开发任何页面/API时必须同时做：

1. 页面级可见性；
