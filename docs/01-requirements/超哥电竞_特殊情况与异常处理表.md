# 超哥电竞｜特殊情况与异常处理表

版本：V0.3  
基线日期：2026-09-23  
用途：作为异常分支、失败恢复、幂等、并发、售后、资金一致性和人工处理的开发基线。

> 本文件与《超哥电竞_业务流程表.md》《超哥电竞_用户权限表.md》配套使用。  
> 正常流程看业务流程表；谁能处理看用户权限表；异常发生后“系统到底怎么办”看本文件。
>
> 2026-09-23 异常规则校对：accepted 可主动取消并回公共池；paid/accepted 可直接全额退款；完成材料支持超时自动通过；投诉期与专属池超时改为配置/快照语义；enabled=false 时 accepted/serving 都回公共池；不引入复杂 Assignment 模型。
>
> 2026-09-23 P0 补充确认：自动审核默认 10 分钟、后台可配置并按每次提交冻结 deadline；同一订单最多一个 pending，驳回重提重新计时；accepted 主动取消必须通知用户且当前不处罚；accepted 退款时打手收益为 0、通知打手并保留 `actualCompanionId`；封禁回池时旧 pending 作废；客服可直接换人且无需管理员批准；换人次数不设上限，由客服判断。

# 1. 异常处理统一原则

每一种异常至少要明确：

1. 谁触发 / 谁检测；
2. 前置状态；
3. 系统立即做什么；
4. 最终进入什么状态；
5. 钱如何变化；
6. 谁负责人工处理；
7. 是否通知；
8. 是否记录审计或领域事件；
9. 是否要求幂等；
10. 当前规则是否已经确认。

状态标识：

| 标记 | 含义 |
|---|---|
| ✅ | 处理规则已确认 |
| 🟡 | 规则已确认，功能正在实现/待验收 |
| ⏳ | 规则已确认，但后续批次实现 |
| ❓ | 尚未确认，不允许开发人员自行决定 |
| ⏸ | 当前明确不做 |

## EX-DISPATCH-08 用户接下自己下的订单（禁止自接单）

| 项目 | 处理 |
|---|---|
| 触发 | `order.userId === 该 Companion 对应的 userId` |
| 适用池 | 公共池与专属池**都适用** |
| 服务端 | accept Guard 强制拒绝；**不依赖前端隐藏**、**不依赖公共池 DTO 是否包含 `userId`** |
| 用户可见结果 | 这一单**不出现在本人的两张池子里**（过滤在服务端 `listCompanionPools`）。⚠️ 这层过滤是**诚实性，不是安全性**：删掉它只会让池子里多一张「点了必然被拒」的单，真正的保护始终是 accept Guard。两者不可互相替代 |
| 为什么只能在服务端做 | 池子 DTO 刻意不含 `userId`（BF-16 / 权限表 §10），因此页面**没有**任何可用判据——过滤只能在服务端做，前端做不到 |
| 指定打手是本人的异常数据 | 即使某用户把自己选成指定打手，仍必须拒绝；该单也不出现在他自己的专属池里 |
| Dispatch | 不变化 |
| Order | 保持原状态 |
| `actualCompanionId` | 不写入 |
| 通知 | 不产生接单成功通知 |
| 其他 Companion | 该订单仍然可被其他合法 Companion 接走 |
| 状态 | 🟡 P0-5 |

| 优惠券成本 | 平台承担 |

### 责任认定（**2026-09-25 产品负责人裁定**，P0-13）

上一行的「打手冲回」公式是**不区分责任**时的取值。裁定后：**退款责任由 Admin 在最终退款决策时认定**，
冲回额按责任类型取值（`refundRate` / `companionLiabilityRate` 一律用**基点 bp**，`10000 = 100%`）：

| 责任类型 | 打手冲回 | 说明 |
|---|---|---|
| `platform`（平台责任） | **0** | 全部由平台承担 |
| `companion`（打手责任） | `floor(companionBaseIncome × refundRateBp / 10000)` | 即上一行的公式 |
| `shared`（共担） | `floor(companionBaseIncome × refundRateBp × companionLiabilityRateBp / 10000 / 10000)` | Admin 同时填写 `companionLiabilityRateBp ∈ [0, 10000]` |

- **不采用**「所有退款一律同比扣打手」。
- `companionLiabilityRate` **只对 `shared` 有意义**；`platform` / `companion` 不填。
- **平台承担额 = `refundAmount − companionReversalAmount`**，即上面的「平台调整」。
- 平台承担部分**必须留下明确、可审计的业务记录**，不能仅通过「没有 reversal」间接推断：
  退款最终决策至少应能读出 `responsibility` · `refundAmount` · `refundRate` · `companionLiabilityRate` ·
  `companionReversalAmount` · `platformBorneAmount` 六项。
- **责任认定权只属于 Admin**；Staff 只能调查、记录、提出处理意见，不得决定退款金额或资金责任。
- 所有金额继续使用**整数分**；**不要求本轮建设完整财务总账**。

**状态｜✅ 2026-09-25 已确认**（责任维度 + 六项可审计字段；P0-13 实现）

# 21. 核心原则汇总

1. **支付/退款/提现等资金事实优先于派生统计。**
2. **真实资金动作不能靠改状态伪装撤销，只能补偿/冲正。**
3. **deadline 是业务事实，scheduler/sweep 只是物化手段。**
4. **所有资金写入、接单、状态推进必须幂等。**
5. **公共池抢单必须原子。**
6. **历史指定打手与实际履约打手不能互相覆盖。**
7. **accepted 后当前实际打手可以主动取消，但必须提交原因并回公共池；serving 后不提供普通主动取消。**
8. **打手不能直接把订单标记 completed；completed 只能来自人工审核通过或满足条件后的系统自动通过。**
9. **投诉存在时不能释放相关冻结收益，也不能删除关键聊天。**
10. **更换打手后新打手不能读取旧打手聊天。**
11. **管理员高风险动作必须审计。**
12. **任何待确认异常都不能由开发人员“顺手选一个方案”。**
13. **禁止自接单：下单用户不能接自己下的单（见 EX-DISPATCH-08）。**
14. **paid / accepted 属于未开始服务，用户可以直接全额退款；serving 后退款进入售后。**
15. **投诉期、公共池超时、专属池超时等生命周期参数改变时，已进入对应阶段的历史订单继续使用自己的 deadline snapshot。**
16. **业务展示阶段不等于 Order.status；waiting_accept / completion_review / settling / settled 由独立领域状态组合得到。**
17. **同一订单同时最多一个 pending CompletionSubmission；驳回后重提重新计时；自动审核默认 10 分钟且按提交冻结 deadline。**
18. **accepted 主动取消必须通知用户，当前 P0 不自动处罚。**
19. **accepted 直接退款时打手收益为 0、通知打手并保留 actualCompanionId 历史事实。**
20. **封禁回池前必须作废旧 pending 完成材料，防止旧材料之后自动完成订单。**
21. **客服可直接换人且无固定换人次数上限；涉及退款资金时管理员仍拥有最终决定权。**
