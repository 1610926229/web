## 2. 核心身份模型

平台基础身份不是四套互相独立账号。

```text
User Session
   ↓
userId
   ├─ 普通用户能力
   └─ Companion（若存在有效资格）→ 打手能力
```

同一个 User 可以同时：
- 作为用户/老板购买服务；
- 作为 Companion/打手提供服务。

Companion 不建立独立 Cookie、独立登录页或第二套 Session。

---

## 3. 主订单状态模型

主订单只描述“订单生命周期”，不承载派单、完成审核、收益、售后等独立生命周期。

| OrderStatus | 含义 |
|---|---|
| `paid` | 已支付，当前没有正在履约的实际打手；可处于专属/公共等待接单阶段 |
| `accepted` | 已有实际打手接单，但尚未开始服务 |
| `serving` | 正在履约 |
| `completed` | 服务已完成；可能来自客服人工审核通过，也可能来自满足规则后的系统自动通过 |
| `refunded` | 已完成全额退款 |

### 3.1 结构状态迁移

当前确认的结构允许关系：

```text
paid      -> accepted | refunded
accepted  -> paid | serving | refunded
serving   -> paid | completed | refunded
completed -> refunded
refunded  -> []
```

其中：

- `accepted → paid`：仅表示打手在**尚未开始服务**时主动取消接单，订单重新回公共池；
- `serving → paid`：当前仅用于**实际打手被 enabled=false / 封禁**时，订单重新回公共池；
- `paid/accepted → refunded`：未开始服务时用户可直接全额退款；
- `serving/completed → refunded`：必须走对应售后/退款规则；
- 结构允许关系不等于业务动作天然合法，具体动作仍必须满足各自权限、原因、资金、幂等和并发 Guard。

### 3.2 业务展示阶段不等于 `Order.status`

用户/后台可以展示更细的业务阶段，但不新增主订单状态：

| 展示阶段 | 底层事实 |
|---|---|
| `waiting_accept` / 等待接单 | `Order.status = paid` + Dispatch 处于可接阶段 |
| `accepted` / 已接单 | `Order.status = accepted` |
| `serving` / 服务中 | `Order.status = serving` 且无 pending 完成材料 |
| `completion_review` / 完成审核中 | `Order.status = serving` + `CompletionSubmission.status = pending` |
| `completed` / 已完成 | `Order.status = completed` |
| `settling` / 结算中 | `Order.status = completed` + Earning/Settlement 仍 frozen |
| `settled` / 已结算 | `Order.status = completed` + Earning/Settlement 已 available |

因此禁止因为 UI 需要展示 `waiting_accept/completion_review/settling/settled`，就把这些字符串直接加入 `OrderStatus`。

独立领域：

| 领域 | 负责内容 |
|---|---|
| Dispatch | 专属池、公共池、接单、超时、重新回池 |
| CompletionSubmission | 完成材料提交、人工审核、自动通过、驳回 |
| Earning / Settlement | 冻结收益、可提现、提现、冲正 |
| AfterSalesCase / Complaint | 投诉、售后、换人、退款建议 |
| Conversation | 当前履约关系的聊天与历史隔离 |

# 5. 金额与分账

## BF-04 原价与实付

当前 V1：

```text
originalAmount = 商品金额 + 全部增值服务金额
```

全部当前增值服务由打手实际履约，因此全部参与打手分账。

优惠券接入后：

```text
actualPaidAmount = originalAmount - couponDiscountAmount
```

当前优惠券尚未正式接入 checkout 计算与核销。

状态：✅ 金额域已实现；优惠券接入 ⏳

## BF-05 打手基础收益

全部金额以整数“分”计算。

```text
companionBaseIncome
= floor(companionRevenueBaseAmount × companionRateSnapshot)
```

当前 V1：

```text
companionRevenueBaseAmount = originalAmount
```

平台基础净收入：

```text
clubNetIncome = actualPaidAmount - companionBaseIncome
```

允许：

```text
clubNetIncome < 0
```

原因：优惠券成本由平台承担，不能通过优惠券降低打手理论基础收益。

状态：✅ 金额计算已实现；真实 Earning 入账 ⏳

# 7. 派单流程

## BF-07 未指定打手

支付成功后：

```text
Dispatch.state = public
```

同时记录：

```text
publicPoolEnteredAt
publicTimeoutMinutesSnapshot
publicDeadlineAt
```

公共池超时时长来自后台平台配置。

规则：
- 在“真正进入公共池”时冻结快照；
- 后台之后修改超时参数，只影响未来进入公共池的订单；
- 已进入公共池的订单 deadline 不变。

状态：✅ P0-5 已实现并验收。

## BF-08 指定打手

假设用户指定 A。

支付成功：

```text
Order.status = paid
Order.actualCompanionId = null

Dispatch.state = exclusive
Dispatch.exclusiveCompanionId = A
```

专属接单期限：

- **由后台平台参数配置**；
- 进入 `exclusive` 时冻结本次 deadline / timeout snapshot；
- 后台后续修改参数，不改变已经进入专属池订单的 deadline。

原“固定 10 分钟”规则已被 2026-09-23 新需求替代。

状态：现有 P0-5 固定时长实现需要后续按新需求整改。

## BF-09 专属池行为

指定打手 A 在**尚未接单**时只有两种行为：

| 行为 | 结果 |
|---|---|
| 接单 | 进入 `accepted` |
| 不操作 | 等待专属 deadline 自动超时 |

接单前仍不存在：
- 主动拒绝；
- “不接”按钮；
- 手动把未接的专属单退回公共池。

“不操作”本身就是不接。

> 注意：这与 `accepted` 后允许主动取消是两件事。接单前不需要“拒绝”；接单后若无法履约，可以按 BF-15 提交原因并取消。

## BF-10 专属池超时

条件：

```text
exclusiveDeadlineAt <= now
```

且尚未接单。

系统：

```text
exclusive → public
```

Order 仍然：

```text
status = paid
```

不会：
- 退款；
- 进入售后；
- 标记失败。

`exclusiveCompanionId` 永久保留历史指定事实。

进入公共池时重新记录：

```text
publicPoolEnteredAt
publicTimeoutMinutesSnapshot
publicDeadlineAt
```

公共池 timeout 使用进入公共池当下的最新平台配置。

状态：P0-5 基础行为已实现；专属 timeout “固定值 → 后台可配置”待整改。

# 8. 公共订单池

## BF-11 公共池范围

当前 V1 不做：
- 游戏匹配过滤；
- 商品匹配过滤；
- 等级匹配；
- 智能推荐；
- 自动分配。

公共池由符合当前接单资格的 Companion 竞争接单。

⚠️ **禁止自接单**：下单用户本人不能接下自己下的订单。公共池与专属池都适用，由服务端 accept Guard 强制拒绝（见 EX-DISPATCH-08）。

⚠️ 这一单**也不会出现在他自己的池子里**。池子返回一份「可接订单」列表，本身就在承诺「这里每一张都接得动」；把他接不了的自己的单放进去，页面就在承诺一件点下去必然失败的事。（过滤是诚实性，accept Guard 才是保护。）

### BR-01 `available=false` 时的业务规则 ✅

2026-09-20 正式确认（原「当前建议方案」原样采纳）：

- `enabled=true + available=false`：仍然是有效 Companion，可以进工作台；
- 公共池不返回可接订单，不能接受新公共池订单；
- 已属于自己的专属派单可以看到，但不能成功 accept；
- 恢复 `available=true` 且 deadline 未过时可以继续接。

关联：PR-01、EX-AUTH-04、Q-EX-01。

## BF-12 原子接单

多个打手可以同时看到公共订单。

接单成功必须同一原子业务区段写入：

```text
Dispatch.state = accepted
Dispatch.acceptedByCompanionId = 当前打手
Dispatch.acceptedAt = now

Order.status = accepted
Order.actualCompanionId = 当前打手
Order.acceptedAt = now
```

必须满足：

```text
Order.actualCompanionId
==
Dispatch.acceptedByCompanionId
```

状态：✅ P0-5 已实现并验收。

## BF-13 指定人与实际履约人分离

# 10. Accepted 状态

## BF-15 接单成功与主动取消

接单成功：

```text
Order.status = accepted
```

含义：

> 已经有实际打手负责，但服务尚未正式开始。

### accepted 后允许实际打手主动取消

只有当前 `actualCompanionId` 对应的打手可以取消自己已经接下、但**尚未开始服务**的订单。

取消要求：

- 必须填写取消原因；
- 至少记录原打手、取消原因、取消时间；
- 客服可在该订单详情中查看取消记录；
- 取消成功后必须通知下单用户订单已重新进入等待接单；
- P0 当前不因本次主动取消自动处罚、罚款或扣减收益；
- 不引入复杂 Assignment 模型，当前只要求保留满足追溯所需的最小历史事实。

取消成功后：

```text
Order.status = paid
当前履约绑定解除
订单重新进入 public Dispatch
```

重新进入公共池时沿用现有公共池规则，重新冻结本次：

```text
publicPoolEnteredAt
publicTimeoutMinutesSnapshot
publicDeadlineAt
```

`serving` 以后不提供普通“主动取消接单”按钮；无法继续履约时走投诉/售后，或由已确认的封禁回池规则处理。

主动取消成功后必须向用户发送生命周期通知；当前 P0 不产生自动处罚。

## BF-16 接单前后信息可见性

### 接单前公共池

只允许看到接单决策所需最小信息。

不得暴露：
- 游戏账号；
- 用户敏感备注；
- 用户其他订单；
- 管理员备注；
- 平台内部信息。

### 接单成功后

实际打手可以查看履约必要信息：
- 订单号；
- 商品；
- 规格；
- 游戏；
- 区服；
- 必要用户信息；
- 游戏账号等必要履约信息；
- 服务要求；
- 用户备注；
- 增值服务。

# 12. 完成材料与审核

## BF-18 打手提交完成材料

只有：
- Order.status = `serving`
- 且操作人 = actualCompanionId

才能提交。

内容：
- 截图/证明材料；
- 5～50 字完成说明。

提交前必须保证同一订单当前不存在另一份 `pending` CompletionSubmission；同一订单同时最多允许 **1 份 pending**。

提交后：

```text
CompletionSubmission.status = pending

autoApprovalMinutesSnapshot = 当前后台自动审核配置
autoApprovalDeadlineAt = submittedAt + autoApprovalMinutesSnapshot
```

自动审核配置默认值为 **10 分钟**。该 snapshot/deadline 在本次提交创建时冻结，后台之后修改配置不影响这份已经 pending 的材料。

如果上一份材料已被客服驳回，允许重新提交；新提交会重新读取当前后台配置并重新开始自动审核计时。

Order 仍保持：

```text
serving
```

业务展示阶段可显示：

```text
completion_review
```

但 `completion_review` **不是新的 Order.status**。

打手不能直接把订单改为 completed。

## BF-19 客服人工审核通过

客服人工审核通过：

```text
Order.status = completed
completedAt = now
CompletionSubmission.status = approved
```

## BF-19A 系统超时自动审核通过

如果：

- 打手已经提交完成材料；
- `CompletionSubmission.status = pending`；
- 到达自动审核 deadline；
- 期间没有用户投诉/有效售后阻塞；
- 尚未被客服人工处理；

则系统可以自动通过：

```text
Order.status = completed
completedAt = now
CompletionSubmission.status = approved
```

自动通过与人工通过产生同一种“已完成”业务事实，但必须记录“系统自动通过”来源，不能伪装成客服人工审核。

自动审核等待时长来自后台配置，**默认 10 分钟**。

每次 CompletionSubmission 进入 `pending` 时冻结：

```text
autoApprovalMinutesSnapshot
autoApprovalDeadlineAt
```

后台之后修改自动审核时长，只影响未来新提交/重新提交的材料，不改变已经 pending 的本次 deadline。

## BF-20 客服审核驳回

驳回：

```text
Order.status 仍为 serving
CompletionSubmission.status = rejected
```

必须记录：
- 驳回原因；
- 审核人；
- 审核时间。

打手可重新提交。

状态：⏳ 后续。

生成实际打手的 Earning。

初始：

```text
Earning.status = frozen
```

状态：⏳

## BF-22 可配置投诉窗口

起点：

```text
completedAt
```

投诉窗口时长来自后台平台配置，不再把“48 小时”写死为不可变规则。

配置口径（2026-09-24 产品裁定）：**默认 24 小时 = 1440 分钟**，单位恒为**分钟**，
取值 **60 ~ 10080 分钟**（1 小时 ~ 7 天）。

订单进入 completed 时冻结本单：

```text
complaintWindowMinutesSnapshot
complaintDeadlineAt
```

> 📌 **字段名以 `complaintWindowMinutesSnapshot` 为准**（2026-09-24 更正，reviewer `m4`）。
> 本文档初版写的是 `complaintWindowSnapshot`，与产品裁定时使用的名字
> （「Order 进入 completed 时冻结 `complaintWindowMinutesSnapshot`」）以及
> 实现 / `database-schema.md` / `lib/types/order.ts` 都不一致。
> 名字分叉的代价是：将来照需求文档写 DB 列名会得到**第二个真值源**，因此这里改为与实现一致。

规则：

# 16. 退款

## BF-26 按服务是否开始区分退款路径

### A. 尚未开始服务：直接全额退款

以下状态都属于“尚未开始服务”：

```text
paid
accepted
```

用户对自己的订单发起退款时：

```text
→ 直接全额退款
→ refundedAmount = actualPaidAmount
→ Order.status = refunded
```

规则：

- 不需要客服审批；
- 不需要管理员决定退款比例；
- 必须幂等；
- `accepted` 虽然已有打手，但只要还没进入 `serving`，仍属于可直接退款范围；
- `accepted` 直接退款时，该打手本单收益为 **0**，不得生成 Earning；
- 必须通知已接单打手该订单已退款；
- `actualCompanionId` **保留**，作为“谁曾实际接下该单”的历史事实，不因终态退款而清空；
- 退款成功后该订单不得继续接单或开始服务。

### B. 已开始服务：进入售后

当：

```text
Order.status = serving
```

用户申请退款：

```text
用户申请退款
→ 进入售后区
→ 客服调查/处理
→ 管理员决定退款比例
→ 系统执行资金变化
```

退款比例可使用既有部分退款规则：

```text
0% ～ 100%
```

管理员只输入退款比例，金额由系统计算。

### C. completed 后

在 `complaintDeadlineAt` 前发生投诉/退款争议时走售后规则，由客服调查，管理员拥有最终资金决定权。

超过普通投诉 deadline 后，普通投诉入口关闭；是否存在特殊人工申诉通道仍是 TBD。

### BR-03 ✅ 已确认（2026-09-23）

旧问题“用户在哪些 Order.status 可以主动申请退款”已确认：

- `paid`：直接全额退款；
- `accepted`：直接全额退款；
- `serving`：可以申请，但进入售后；
- `completed`：投诉窗口内走售后；
- `refunded`：不得再次退款。

# 17. 部分退款资金公式

输入：

```text
refundRate ∈ [0, 10000] bp
```

用户退款：

```text
userRefundAmount
= floor(actualPaidAmount × refundRate)
```

打手冲回：

```text
companionReversal
= floor(companionBaseIncome × refundRate)
```

平台调整：

```text
clubIncomeAdjustment
= userRefundAmount - companionReversal
```

必须保持：

```text
userRefundAmount
=
companionReversal + clubIncomeAdjustment
```

打手最终：

```text
companionFinalIncome
= companionBaseIncome - companionReversal
```

平台最终：

```text
clubFinalNetIncome
= clubNetIncome - clubIncomeAdjustment
```

允许：

```text
clubIncomeAdjustment < 0
```

状态：规则已冻结；真正 Earning/退款联动 ⏳。
