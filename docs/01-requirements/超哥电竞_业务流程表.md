## 2. 核心身份模型

平台基础身份不是四套互相独立账号。

```text
User Session
   ↓
userId
   ├─ 普通用户能力
   └─ Companion（若存在有效资格）→ 打手能力
```

同一个 User 可以同时：
- 作为用户/老板购买服务；
- 作为 Companion/打手提供服务。

Companion 不建立独立 Cookie、独立登录页或第二套 Session。

---

## 3. 主订单状态模型

主订单只描述“订单生命周期”，不承载派单、完成审核、收益、售后等独立生命周期。

| OrderStatus | 含义 |
|---|---|
| `paid` | 已支付，等待派单/接单 |
| `accepted` | 已有实际打手接单，但尚未开始服务 |
| `serving` | 正在履约 |
| `completed` | 服务经客服审核完成 |
| `refunded` | 已退款 |

独立领域：

| 领域 | 负责内容 |
|---|---|
| Dispatch | 专属池、公共池、接单、超时 |
| CompletionSubmission | 完成材料提交、审核通过/驳回 |
| Earning / Settlement | 冻结收益、可提现、提现、冲正 |
| AfterSalesCase / Complaint | 投诉、售后、换人、退款建议 |
| Conversation | 当前 assignment 的聊天与历史隔离 |

# 5. 金额与分账

## BF-04 原价与实付

当前 V1：

```text
originalAmount = 商品金额 + 全部增值服务金额
```

全部当前增值服务由打手实际履约，因此全部参与打手分账。

优惠券接入后：

```text
actualPaidAmount = originalAmount - couponDiscountAmount
```

当前优惠券尚未正式接入 checkout 计算与核销。

状态：✅ 金额域已实现；优惠券接入 ⏳

## BF-05 打手基础收益

全部金额以整数“分”计算。

```text
companionBaseIncome
= floor(companionRevenueBaseAmount × companionRateSnapshot)
```

当前 V1：

```text
companionRevenueBaseAmount = originalAmount
```

平台基础净收入：

```text
clubNetIncome = actualPaidAmount - companionBaseIncome
```

允许：

```text
clubNetIncome < 0
```

原因：优惠券成本由平台承担，不能通过优惠券降低打手理论基础收益。

状态：✅ 金额计算已实现；真实 Earning 入账 ⏳

## BF-06 支付成功

支付成功后创建 Order。

初始：

```text
Order.status = paid
```

即使用户指定了打手 A：

```text

```

因为：
- `exclusiveCompanionId` = 用户指定的人；
- `actualCompanionId` = 最终真正接单的人。

状态：✅ 已实现。

# 7. 派单流程

## BF-07 未指定打手

支付成功后：

```text
Dispatch.state = public
```

同时记录：

```text
publicPoolEnteredAt
publicTimeoutMinutesSnapshot
publicDeadlineAt
```

公共池超时时长来自后台平台配置。

规则：
- 在“真正进入公共池”时冻结快照；
- 后台之后修改超时参数，只影响未来进入公共池的订单；
- 已进入公共池的订单 deadline 不变。

状态：🟡 P0-5 已开发，待最终验收。

## BF-08 指定打手

假设用户指定 A。

支付成功：

```text
Order.status = paid
Order.actualCompanionId = null

Dispatch.state = exclusive
Dispatch.exclusiveCompanionId = A
```

专属接单期限：

```text
10 分钟
```

10 分钟为产品固定规则，不作为平台可配置参数。

状态：🟡 P0-5 已开发，待最终验收。

## BF-09 专属池行为

指定打手 A 只有两种行为：

| 行为 | 结果 |
|---|---|
| 接单 | 进入 `accepted` |
| 不操作 | 等待 10 分钟自动超时 |

不存在：
- 主动拒绝；
- 放弃；
- “不接”按钮；
- 主动退回公共池。

“不操作”本身就是不接。

## BF-10 专属池超时

条件：

```text
exclusiveDeadlineAt <= now
```

且尚未接单。

系统：

```text
exclusive → public
```

Order 仍然：

```text
status = paid
```

不会：
- 退款；
- 进入售后；
- 标记失败。

`exclusiveCompanionId` 永久保留。

进入公共池时重新记录：

```text
publicPoolEnteredAt
publicTimeoutMinutesSnapshot
publicDeadlineAt
```

公共池 timeout 使用进入公共池当下的最新平台配置。

状态：🟡 P0-5 已开发，待最终验收。

# 8. 公共订单池

## BF-11 公共池范围

当前 V1 不做：
- 游戏匹配过滤；
- 商品匹配过滤；
- 等级匹配；
- 智能推荐；
- 自动分配。

公共池由符合当前接单资格的 Companion 竞争接单。

⚠️ **禁止自接单**：下单用户本人不能接下自己下的订单。公共池与专属池都适用，由服务端 accept Guard 强制拒绝（见 EX-DISPATCH-08）。

⚠️ 这一单**也不会出现在他自己的池子里**。池子返回一份「可接订单」列表，本身就在承诺「这里每一张都接得动」；把他接不了的自己的单放进去，页面就在承诺一件点下去必然失败的事。（过滤是诚实性，accept Guard 才是保护。）

### BR-01 `available=false` 时的业务规则 ✅

2026-09-20 正式确认（原「当前建议方案」原样采纳）：

- `enabled=true + available=false`：仍然是有效 Companion，可以进工作台；
- 公共池不返回可接订单，不能接受新公共池订单；
- 已属于自己的专属派单可以看到，但不能成功 accept；
- 恢复 `available=true` 且 deadline 未过时可以继续接。

关联：PR-01、EX-AUTH-04、Q-EX-01。

## BF-12 原子接单

多个打手可以同时看到公共订单。

接单成功必须同一原子业务区段写入：

```text
Dispatch.state = accepted
Dispatch.acceptedByCompanionId = 当前打手
Dispatch.acceptedAt = now

Order.status = accepted
Order.actualCompanionId = 当前打手
Order.acceptedAt = now
```

必须满足：

```text
Order.actualCompanionId
==
Dispatch.acceptedByCompanionId
```

状态：🟡 P0-5 已开发，待最终验收。

## BF-13 指定人与实际履约人分离

示例：

```text
用户指定 A
A 10 分钟未接
→ 进入公共池
B 接单
```

```text
exclusiveCompanionId = A
acceptedByCompanionId = B
actualCompanionId = B
```

- 指定护航：A
- 实际接单：B

# 9. 公共池超时

## BF-14 公共池无人接单

条件：

```text
publicDeadlineAt <= now
```

且 Dispatch 仍为 `public`。

系统自动：

```text

refundedAmount = actualPaidAmount
```

规则：
- 全额自动退款；
- 不需要客服；
- 不需要管理员审批；
- 当前规则不自动创建普通售后案件；
- 不允许超时后继续接单；
- repeated sweep 不重复退款；
- repeated sweep 不重复通知。

状态：🟡 P0-5 已开发，待最终验收。

# 10. Accepted 状态

## BF-15 接单成功

接单成功：

```text
Order.status = accepted
```

含义：

> 已经有实际打手负责，但服务尚未正式开始。

打手接单之后不能主动：
- 放弃；
- 退单；
- 丢回公共池；
- 自行更换打手。

无法履约时走投诉/售后流程。

## BF-16 接单前后信息可见性

### 接单前公共池

只允许看到接单决策所需最小信息。

不得暴露：
- 游戏账号；
- 用户敏感备注；
- 用户其他订单；
- 管理员备注；
- 平台内部信息。

### 接单成功后

实际打手可以查看履约必要信息：
- 订单号；
- 商品；
- 规格；
- 游戏；
- 区服；
- 必要用户信息；
- 游戏账号等必要履约信息；
- 服务要求；
- 用户备注；
- 增值服务。

# 11. 开始服务

## BF-17 accepted → serving

只能由：

```text

```

对应的实际打手点击“开始服务”。

状态转换：

```text
accepted → serving
```

不允许：
- 根据时间自动开始；
- 根据预约备注自动开始；
- 打开页面自动开始；
- 聊天开始自动触发；
- 客服代替打手走普通“开始服务”。

预约不开发独立预约系统，预约时间通过用户备注/服务要求表达。

# 12. 完成材料与审核

## BF-18 打手提交完成材料

只有：
- Order.status = `serving`
- 且操作人 = actualCompanionId

才能提交。

内容：
- 截图/证明材料；
- 5～50 字完成说明。

提交后：

```text
CompletionSubmission.status = pending
```

Order 仍保持：

```text
serving
```

打手不能直接把订单改为 completed。

## BF-19 客服审核通过

通过：

```text
Order.status = completed
completedAt = now
CompletionSubmission.status = approved
```

## BF-20 客服审核驳回

驳回：

```text
Order.status 仍为 serving
CompletionSubmission.status = rejected
```

必须记录：
- 驳回原因；
- 审核人；
- 审核时间。

打手可重新提交。

状态：⏳ 后续。

# 17. 部分退款资金公式

输入：

```text
refundRate ∈ [0, 10000] bp
```

用户退款：

```text
userRefundAmount
= floor(actualPaidAmount × refundRate)
```

打手冲回：

```text
companionReversal
= floor(companionBaseIncome × refundRate)
```

平台调整：

```text
clubIncomeAdjustment
= userRefundAmount - companionReversal
```

必须保持：

```text
userRefundAmount
=
companionReversal + clubIncomeAdjustment
```

打手最终：

```text
companionFinalIncome
= companionBaseIncome - companionReversal
```

平台最终：

```text
clubFinalNetIncome
= clubNetIncome - clubIncomeAdjustment
```

允许：

```text
clubIncomeAdjustment < 0
```

状态：规则已冻结；真正 Earning/退款联动 ⏳。

# 26. 生产上线硬性要求

## 真实并发

当前 Mock 的 Node 单进程“无 await 原子区段”不能替代真实数据库事务。

上线前必须：

```text
数据库 transaction
+
必要唯一约束 / 并发约束
```

## 真实定时任务

当前 Mock 可以 lazy sweep。

生产必须：

```text
Cron / Worker / Scheduler
→ 调用同一套领域 Service
```

禁止再写第二套 timeout/refund 逻辑。

## 真实登录

Mock Auth 最终替换微信公众号 OAuth。

Companion 仍然保持：

```text
User → Companion capability
```

不得重新建立打手独立账号体系。

## 真实支付

Mock Payment 最终替换真实微信支付/退款。
